Data flow

한 문장으로 보는 구조

Codex는 MemoryGraph 내부 구조를 직접 알 필요가 없다. Hook이 작업 문맥을 Wrapper에 넘기면 Wrapper가 프로젝트 전용 DB에서 기억을 찾아 짧은 JSON으로 돌려준다.

Decisions 01–32

확정된 32개 결정

각 항목은 구현자가 다시 선택하지 않아도 되는 기본값이다. 핵심 키워드는 바로 아래에 쉬운 뜻을 함께 적었다.

A · 역할과 범위

01
MemoryGraph는 장기 기억 정본이다.

정본은 같은 사실을 최종적으로 믿는 저장 위치다. 진행 상태는 State Store가 맡는다.

02
Wrapper는 하네스와 MemoryGraph 사이의 어댑터다.

Wrapper는 외부 라이브러리의 복잡한 사용법을 우리 명령 하나로 감싸는 얇은 코드다.

03
v1의 첫 범위는 Recall이다.

Recall은 현재 작업과 관련된 과거 기억을 찾아 Codex 문맥에 넣는 과정이다.

04
후보 생성·최종 저장은 별도 흐름으로 유지한다.

이번 Wrapper 구현에 Memory Candidate 평가나 관계 생성을 섞지 않는다.

05
MemoryGraph 원본을 복제 구현하지 않는다.

공식 구현을 재사용하고, 우리 정책만 Wrapper에 둔다.

06
전역 설치는 개발 확인용일 뿐 정본 의존성이 아니다.

다른 컴퓨터에서도 같은 코드를 쓰도록 프로젝트가 참조 버전을 보유한다.

B · 의존성과 버전

07
공식 저장소를 Git submodule로 연결한다.

Submodule은 외부 Git 저장소의 특정 커밋을 프로젝트 안의 경로로 고정하는 방법이다.

08
경로는 vendor/memory-graph다.

vendor는 프로젝트가 고정해서 사용하는 외부 소스 코드를 모으는 디렉터리다.

09
브랜치가 아니라 정확한 커밋을 고정한다.

main이 바뀌어도 우리 빌드 결과가 갑자기 달라지지 않게 한다.

10
Submodule의 목적은 재현성과 안정적인 import 경로다.

저작권을 피하기 위한 우회가 아니다. 공식 MIT 라이선스와 고지를 그대로 유지한다.

11
Runtime은 Bun을 사용한다.

Runtime은 TypeScript 코드를 실제로 실행하는 프로그램이다. MemoryGraph v0.13.0은 Bun ≥ 1.1을 요구한다.

12
의존성 설치는 lockfile을 고정해 수행한다.

bun install --frozen-lockfile로 기록되지 않은 의존성 변경을 막는다.

C · 저장소와 연결 방식

13
MemoryGraph backend는 SQLite를 사용한다.

Backend는 기억이 실제로 저장되고 검색되는 저장 엔진이다.

14
기억 DB는 .harness/memorygraph.db다.

이 프로젝트의 장기 기억만 담는 로컬 SQLite 파일이다.

15
State DB와 MemoryGraph DB를 분리한다.

state.db는 현재 작업 상태, memorygraph.db는 재사용할 장기 지식을 저장한다.

16
MemoryGraph DB 파일은 Git으로 추적하지 않는다.

DB 본체와 -wal·-shm 보조 파일 모두 로컬 런타임 데이터다.

17
FalkorDBLite는 초기 경로에서 제외한다.

현재 환경의 저장·검색 호환성 문제가 있어 검증된 SQLite 경로를 우선한다.

18
CLI 문자열 출력을 파싱하지 않는다.

사람에게 보여주는 출력 형식은 바뀌기 쉬우므로 프로그램 데이터 계약으로 사용하지 않는다.

D · MemoryGraph API 경계

19
SQLiteBackend를 직접 사용한다.

MemoryGraph의 SQLite 저장·조회 기능을 제공하는 클래스다.

20
검색은 searchMemories()를 호출한다.

검색어와 제한 수를 받아 Memory 객체 목록을 돌려주는 MemoryGraph 함수다.

21
최상위 ts/src/index.ts는 import하지 않는다.

가져오기만 해도 CLI main()이 실행되는 부작용이 있기 때문이다.

22
ts/src/backends/sqlite.ts를 직접 import한다.

Wrapper가 사용하는 내부 모듈 경계를 한곳으로 제한한다.

23
내부 import는 Wrapper 밖으로 노출하지 않는다.

MemoryGraph 구조가 바뀌어도 Wrapper만 고치도록 우리 코드와 외부 코드를 분리한다.

24
새 정식 태그가 나올 때만 업그레이드를 검토한다.

MemoryGraph 자체 테스트와 우리 Wrapper 계약 테스트를 모두 통과한 뒤 커밋을 바꾼다.

E · Recall 실행과 결과 정책

25
Recall은 start_work() 성공 직후 실행한다.

전용 PostToolUse Hook에서 WI·Run·intent가 확정된 뒤 호출한다.

26
입력은 짧은 키워드 목록이다.

긴 자연어 문장보다 기술명·파일명·도구명처럼 구별되는 단어를 사용한다.

27
Wrapper가 키워드를 정규화한다.

공백 제거, 빈 값 제거, 중복 제거를 수행한 뒤 각 키워드를 독립 검색한다.

28
키워드마다 searchMemories()를 호출한다.

여러 단어를 하나의 연속 문장으로 LIKE 검색해 놓치는 문제를 피한다.

29
결과는 Memory ID로 병합한다.

같은 기억이 여러 검색에서 발견돼도 최종 결과에는 한 번만 넣는다.

30
여러 키워드에 걸린 기억을 우선한다.

1차 점수는 서로 다른 키워드 검색에서 발견된 횟수다. 동점은 중요도와 최신순으로 정렬한다.

31
Codex에는 상위 3–5개만 짧게 전달한다.

원본 전체가 아니라 ID·제목·요약·매칭 키워드만 담은 Context Packet을 사용한다.

32
Recall 실패는 본 작업을 막지 않는다.

경고와 오류 종류를 남기고 빈 기억 결과로 계속한다. 일부 키워드만 실패하면 성공한 결과를 사용한다.

Pinned release

선택한 안정 버전

여기서 안정은 오류가 전혀 없다는 뜻이 아니라, 정식 태그이고 우리가 사용할 SQLite 검색 경로를 실제 테스트로 재검증했다는 뜻이다.

Recommended pinMemoryGraph v0.13.067fc4f97816aa75823ae2dd4eff49f150cc6f1da
현재 최신 정식 릴리스

움직이는 main 대신 버전 의미와 재현성이 분명하다.

현재 설계와 같은 세대

TypeScript/Bun의 SQLiteBackend와 searchMemories()를 제공한다.

직접 재검증 완료

Bun 1.3.9에서 97/97 테스트와 TypeScript typecheck가 통과했다.

태그 이후 변경은 v1 필수 기능이 아님

미출시 main의 offset·관계 탐색 보강은 초기 Recall에서 사용하지 않는다.

주의: v0.13.0은 1.0 이전이며 TypeScript 전환 첫 릴리스다. 그래서 내부 import를 Wrapper 한곳에 가두고 정확한 SHA를 고정한다. 공식 근거는 릴리스와 커밋에서 확인한다.

Public contract

Wrapper 입·출력 계약

계약은 내부 구현이 바뀌어도 호출자가 믿을 수 있는 입력과 출력 규칙이다. 첫 구현은 아래 값을 기준으로 한다.

외부 명령

Hook과 사람이 공통으로 사용할 프로젝트 전용 CLI다.

harness-memory recall \
  "sqlite 외래키 상태저장소" \
  --limit 5

내부 함수 입력

문자열 CLI 입력은 경계에서 배열로 바꾸며, 핵심 함수는 명시적인 구조를 받는다.

recallMemories({
  keywords: ["sqlite", "외래키", "상태저장소"],
  limit: 5
})

성공 JSON

Codex에는 MemoryGraph 원본 객체 전체가 아니라 작업에 필요한 최소 필드만 반환한다.

{
  "ok": true,
  "memories": [
    {
      "id": "mem_123",
      "title": "SQLite 외래키 활성화",
      "summary": "DB 연결 직후 PRAGMA foreign_keys = ON을 실행한다.",
      "matched_keywords": ["sqlite", "외래키"]
    }
  ],
  "warnings": []
}

빈 결과

검색 결과 없음은 오류가 아니다. 정상 응답의 빈 배열로 표현한다.

{
  "ok": true,
  "memories": [],
  "warnings": []
}

검색 실패

본 작업을 계속할 수 있도록 기계적으로 읽을 수 있는 경고를 반환한다.

{
  "ok": false,
  "memories": [],
  "warnings": ["memory_database_unavailable"]
}

정렬 규칙

순서기준쉬운 의미
1matched_keywords.length 내림차순더 많은 검색 키워드에 함께 걸린 기억을 먼저 둔다.
2MemoryGraph 중요도 내림차순키워드 점수가 같으면 더 중요하게 저장된 기억을 우선한다.
3생성·갱신 시각 내림차순앞의 조건까지 같으면 더 최근 기억을 우선한다.
4Memory ID 오름차순완전히 동점일 때도 결과 순서가 실행마다 흔들리지 않게 한다.

입력 기본값: 빈 키워드와 중복은 제거하고, 유효 키워드가 없으면 DB를 호출하지 않은 채 빈 성공 결과를 반환한다. limit 기본값은 5이며 구현에서는 1–10 범위로 제한한다.

Module boundary

권장 코드 구조

CLI 입출력, 검색 정책, 외부 MemoryGraph 연결을 분리하면 테스트가 쉬워지고 upstream 변경도 한 파일에서 흡수할 수 있다.

memory/client.ts

Vendored SQLiteBackend를 import하고 연결·검색하는 유일한 파일. 외부 라이브러리 변경을 흡수하는 경계다.

memory/recall.ts

키워드 정규화, 반복 검색, ID 병합, 정렬, 제한을 수행하는 핵심 함수다.

memory/cli.ts

harness-memory recall 인자를 읽고 항상 JSON을 stdout에 출력하는 얇은 명령 진입점이다.

memory/types.ts

입력·응답·경고 코드처럼 Wrapper가 공개하는 객체 구조를 정의한다.

Implementation status

현재 구현 상태

Recall Wrapper, 독립 실행 CLI와 start_work 전용 PostToolUse Hook까지 구현하고 검증했다.

Submodule 고정 · 완료공식 저장소와 정확한 SHA가 Git에 기록됐다.
Client 경계 · 완료프로젝트 DB 연결과 searchMemories() 호출을 구현했다.
Recall 정책 · 완료정규화·검색·병합·결정적 정렬을 테스트했다.
CLI 제공 · 완료bin/harness-memory recall이 JSON 계약을 제공한다.
Hook 통합 · 완료start_work PostToolUse가 Binding을 저장하고 Context Packet을 주입한다.

검증통과 조건

DB 장애Run을 취소하지 않고 구조화된 경고와 빈 목록을 반환한다.

Explicitly out of scope

첫 구현에서 하지 않는 것

아래 항목은 버린 것이 아니라 Recall Wrapper의 첫 범위에서 분리한 후속 작업이다.

Memory Candidate 최종 저장

후보 평가·promote·reject는 Memory Finalize Skill에서 구현한다.

관계 그래프 탐색

초기 Recall은 텍스트 검색 결과만 사용하고 BFS 관계 확장은 하지 않는다.

FalkorDBLite 지원

SQLite 계약이 안정된 뒤 호환성 문제와 필요성을 다시 평가한다.

전역·다중 프로젝트 기억 통합

각 프로젝트의 memorygraph.db를 분리하며 공유 저장소는 설계하지 않는다.

MemoryGraph 내부 코드 수정

필요한 정책은 Wrapper에 두고 upstream fork는 만들지 않는다.

Recall 실패로 작업 차단

장기 기억은 보조 문맥이므로 상태 저장소처럼 필수 전제 조건으로 취급하지 않는다.
