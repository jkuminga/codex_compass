01 · Boundary

Codex는 판단하고, 도구는 실행한다

Memory Finalize Skill은 저장할 가치와 관계를 판단해 Storage Plan을 만든다. finalize_memory_candidate()는 그 계획이 안전한지 검사하고 같은 순서로 실행한다. MCP 안에서 새로운 LLM 추론을 수행하지 않는다.

입력

Storage Plan

Codex가 결정한 create·merge·reject, 최종 기억 내용, 연결할 기존 Memory ID를 담는다.

실행

Finalize MCP

후보 상태·타입·점수·관계 대상·중복 여부를 검사한 뒤 MemoryGraph Writer를 호출한다.

결과

Receipt

생성·병합된 Memory ID, 관계 처리 결과, 후보의 최종 상태와 재시도 가능 여부를 짧은 JSON으로 반환한다.

03 · Runtime

Finalize 내부 처리 순서

후보·저장 계획 확인candidate_id로 State DB 후보를 읽고 반드시 pending인지 확인한다. 저장 계획이 처음이면 정규화한 원문과 plan_fingerprint를 State DB에 먼저 기록한다. 이미 계획이 있으면 그 계획을 재사용하며, 이미 마감된 후보는 동일 결과만 안전하게 반환하고 다른 계획은 충돌로 거부한다.
입력 정규화·검증MemoryType·RelationshipType, 제목·내용 길이, 점수 0~1, 관계 방향과 대상 ID를 MemoryGraph에 쓰기 전에 검사한다.
노드 저장 또는 병합create는 candidate:<candidate_id> 결정적 ID를 사용한다. merge는 target_memory_id만 갱신하며 임의의 다른 기억을 수정하지 않는다.
관계 생성결과 노드 ID가 확정된 다음 관계를 만든다. 같은 from + to + type이면 중복 생성하지 않고 skipped로 기록한다.
후보 마감·Receipt노드와 모든 관계가 성공한 경우에만 finalize_memory_candidate() 내부에서 promote_memory_candidate()를 호출해 State DB의 memory_ref를 기록하고 promoted로 바꾼다. 실패하면 후보는 pending으로 남긴다.
두 DB는 하나의 트랜잭션이 아니다

State DB와 MemoryGraph가 서로 다른 SQLite 파일이므로 전체를 한 번에 되돌릴 수 없다. 따라서 도구는 Saga처럼 단계별 결과를 확인하고, MemoryGraph 쓰기 전에 State DB에 최초 Storage Plan을 보존한다. 중간 실패는 partial Receipt로 알리고, 다음 호출은 그 Plan을 다시 읽어 같은 후보의 남은 단계만 재시도한다.

04 · Implemented safety decisions

구현된 4가지 안전 조건

아래 항목은 단순한 품질 개선이 아니라 잘못된 승격·중복 기억·복구 불가능한 상태를 막기 위한 필수 체크리스트다.

  • 후보 상태는 모든 쓰기 성공 뒤에만 변경finalize_memory_candidate()가 노드·관계 쓰기를 모두 성공시킨 뒤 내부에서 promote_memory_candidate()를 호출한다. 하나라도 실패하면 promote를 호출하지 않고 후보를 pending으로 유지한다.
  • 중복 저장과 다른 계획 덮어쓰기 방지create는 결정적 Memory ID를 쓰고, 관계는 from + to + type 조합을 재사용한다. 같은 후보를 다시 처리할 때는 동일한 Storage Plan만 재시도하고, 내용·관계·결정이 다른 계획이면 충돌로 거부한다. 다른 후보가 같은 기존 기억에 정상적으로 merge하는 것은 막지 않는다.
  • 부분 실패를 재시도 가능하게 처리첫 호출에서 Storage Plan 원문과 plan_fingerprint를 State DB에 저장한다. 중간 오류가 나면 partial 결과와 짧은 오류 코드를 반환하고 후보는 pending으로 유지한다. 다음 호출은 저장된 Plan을 새로 추론하지 않고 재사용해 기존 노드·관계를 확인한 뒤 빠진 부분만 처리한다.
  • 입력 필드와 관계 방향 고정decision은 create·merge·reject만 허용하고, memory의 타입·제목·내용·점수와 relationships의 방향·타입·대상 ID를 검증한다. 관계의 대상 Memory가 실제로 존재하는지와 자기 자신을 가리키지 않는지도 확인한 뒤 Adapter에서 MemoryGraph의 from/to/type으로 변환한다.
검증 실패는 쓰기 전에 멈춘다

필수 필드 누락, 점수 범위 오류, 허용되지 않은 관계 타입·방향, 존재하지 않는 대상 ID가 하나라도 있으면 MemoryGraph를 호출하지 않는다. validation_error와 실패 필드만 짧게 반환해 Codex가 계획을 고쳐 다시 호출할 수 있게 한다.

merge 재시도 규칙

create는 후보 ID로 노드 ID를 만들 수 있지만 merge는 기존 노드를 수정한다. 따라서 후보별 Storage Plan을 정규화한 plan_fingerprint로 재시도를 구분한다. 같은 후보·같은 지문이면 기존 Receipt를 재사용하고, 다른 지문이면 기존 저장을 덮어쓰지 않고 충돌로 거부한다. 이 검사는 다른 후보가 같은 target_memory_id에 유효한 계획으로 merge하는 것까지 차단하지 않는다.

05 · Wired

연결 완료된 5가지

저장 Module만 만들어서는 Codex 흐름에 들어오지 않는다. 아래 연결이 모두 끝나야 실제 Work Finish에서 사용할 수 있다.

  • harness-memory MCP에 도구 등록finalize_memory_candidate를 Python Adapter에 노출하고 .codex/config.toml의 허용 도구 목록에 추가한다.
  • PreToolUse에서 활성 Run 요구읽기용 inspect와 달리 finalize는 MemoryGraph·State DB를 변경하므로 유효한 Runtime Binding과 활성 Run 없이는 거부한다.
  • Python Adapter → TypeScript Writer 연결Python은 후보 조회·MCP 계약·상태 마감을 담당하고, TypeScript는 MemoryGraph v0.13.0의 SQLiteBackend를 담당한다. JSON stdin/stdout 경계를 유지한다.
  • create·merge·reject와 재시도 테스트 작성정상 저장, 같은 계획 재호출, 다른 계획 충돌, 중복 관계, 후보 없음·비-pending을 모두 검증한다.
  • 성공 뒤에만 promote_memory_candidate 실행MemoryGraph 노드와 관계 처리가 완전히 끝난 경우에만 finalize_memory_candidate() 내부에서 promote_memory_candidate()를 호출한다. work-finish는 promote를 별도로 호출하지 않는다.

06 · Scope guard

이번 구현에서 하지 않는 것

다중 노드 분해후보 하나를 여러 주 노드로 나누는 기능은 후속 확장으로 둔다.
새로운 LLM 호출MCP 도구 내부에서 저장 가치나 관계를 다시 추론하지 않는다.
자동 Stop Hook 호출이번 도구는 Work Finish Skill이 명시적으로 호출한다.
완료 후 사용 흐름

work-finish가 pending 후보를 찾고 → inspect_memory_candidate()를 호출한다. 저장 계획이 없으면 Memory Finalize Skill이 Storage Plan을 만들고, 있으면 저장된 Plan을 그대로 재사용한다 → finalize_memory_candidate()를 호출한다. 노드·관계 저장이 모두 성공하면 이 도구가 내부에서 promote_memory_candidate()를 호출하며, work-finish가 promote를 따로 호출하지 않는다.
