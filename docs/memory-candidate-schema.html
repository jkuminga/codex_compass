Harness v2 · staging schema

장기 기억 후보 저장 스키마

Codex가 작업 중 기억 후보를 발견하면 그 자리에서 한 건씩 SQLite에 저장한다. 종료 전 검토에서 기존 기억과 함께 비교한 뒤, 통과한 노드와 그 관계만 MemoryGraph에 저장한다.

1후보 저장 테이블
13기억 타입 초안
즉시후보 단건 저장

전체 구조

Run은 한 번의 작업 실행이다. 작업 중 후보를 발견할 때마다 바로 저장하고, 종료 전 검토가 노드와 관계를 확정한 뒤 실제 MemoryGraph ID를 후보 행에 되돌려 적는다.

작업 중에는 후보 저장에만 집중한다. 문제와 해결책은 발견하는 즉시 각각 한 행으로 저장한다. SOLVES 같은 관계는 종료 전 검토가 기존 MemoryGraph 노드까지 확인한 뒤 만든다.

핵심 용어

필드 이름의 proposed는 “검토 후 바뀔 수 있는 초안”이라는 뜻이다.

Memory Candidate
MemoryGraph 기억 노드가 될 수 있는 검토 전 초안
Promotion
검토를 통과한 후보를 실제 MemoryGraph에 저장하는 과정
Memory Reference
MemoryGraph에 저장된 기억을 가리키는 ID
Finalization
후보를 검토하고 노드 저장·병합·폐기와 관계 생성을 한 번에 결정하는 종료 전 단계

필드 사전

memory_candidates는 작업 중 발견한 장기 기억 후보를 즉시 보관하는 유일한 후보 테이블이다.

필드형식필수쉬운 설명

검색 조건에 맞는 필드가 없습니다.

memory_candidates.proposed_type · 13개

설계 결정은 별도 decision 타입이 없으므로 solution 타입과 decision 태그를 함께 쓴다.

후보 노드 · 작업 중 입력 원칙

짧은 제목핵심 내용검색 키워드현재 상태

점수·검토 상세·근거·컨텍스트는 후보 행에 미리 저장하지 않고 종료 전 검토에서 필요한 만큼만 사용한다.

상태 의미

pending

아직 최종 검토하지 않았다. 후보 노드의 memory_ref는 비어 있다.

promoted

MemoryGraph에 저장하거나 기존 기억에 반영했다. 후보 노드에는 실제 memory_ref가 필요하다.

rejected

장기 기억으로 남기지 않기로 했다. 후보 노드는 상태만 남기고 실제 기억 참조를 만들지 않는다.

  • run_id는 존재하는 Run이어야 하며 WorkItem은 후보 → Run → WorkItem으로 계산한다.
  • title은 1~200자, content는 비어 있을 수 없다.
  • keywords_json은 문자열 배열이며 SQLite json_valid()를 통과해야 한다.
  • proposed_type은 MemoryGraph가 허용하는 13개 기억 타입 중 하나다.
  • pending과 rejected에서는 memory_ref가 비어 있어야 한다.
  • promoted에서는 memory_ref가 반드시 있어야 한다.
  • 후보 중복 판단과 저장 가치 채점은 종료 전 검토에서 수행한다.
  • 상세 근거와 검토 판단은 후보 필드가 아니라 Run Trace와 Artifact에서 찾는다.

관계는 최종 검토에서 판단

후보 DB에는 관계를 저장하지 않는다. 실제로 남길 노드가 확정되고 기존 MemoryGraph 기억을 조회한 뒤 관계를 한 번에 판단한다.

기존·신규 노드 전체

내용을 비교해 SOLVES 등의 관계 생성

예: 작업 중 문제 후보와 해결책 후보를 각각 즉시 저장한다. 종료 전 검토가 두 후보와 기존 기억을 함께 읽고, 둘이 실제로 저장될 때만 해결책 --SOLVES--> 문제 관계를 MemoryGraph에 직접 만든다.

  • 현재 Run의 pending 후보를 모두 읽는다.
  • MemoryGraph에서 유사하거나 관련된 기존 기억을 조회한다.
  • 후보별로 신규 저장, 기존 기억 병합, 폐기를 결정한다.
  • 실제로 남는 노드들만 관계 판단 대상으로 사용한다.
  • 관계 타입·방향·강도는 최종 노드 내용을 기준으로 정한다.
  • 확정한 관계는 후보 DB를 거치지 않고 MemoryGraph에 직접 저장한다.
  • 근거가 약하면 관계를 만들지 않는다.
  • 관계 저장 실패 시 해당 후보는 완료 처리하지 않고 재시도할 수 있게 남긴다.

검토와 승격

작업 중에는 후보를 발견 즉시 한 건씩 저장한다. 종료 전 한 번의 검토에서 기존 기억 검색·중복 판단·노드 저장·관계 생성을 수행한다. 아래 평가는 후보 필드로 저장하지 않는 일시적인 판단값이다.

importance

이 기억을 미래 작업에서 다시 사용할 가치가 얼마나 큰가?

confidence

내용 또는 관계가 사실이라고 얼마나 확신하는가?

review_score

하네스의 최종 저장 기준을 전체적으로 얼마나 충족했는가?

최종 처리 순서

01pending 조회
02저장 가치 채점
03기존 기억 검색
04저장·병합·폐기 결정
05노드 저장
06memory_ref 확보
07전체 노드 관계 판단
08관계 저장·상태 갱신
09pending 없음 확인

MemoryGraph 저장이 실패하면 후보를 억지로 완료 처리하지 않고 pending으로 남긴다. 다음 검토에서 다시 시도할 수 있기 때문이다.

단건 입력 예시와 DDL

create_candidate는 기억 후보를 발견한 순간 한 건만 저장한다. 배치 입력과 후보 관계 입력은 제공하지 않는다.

{
  "run_id": "RUN-20260810-001",
  "proposed_type": "problem",
  "title": "인증 토큰 만료 시간이 너무 짧음",
  "content": "Access Token 만료 시간이 짧아 사용자가 반복해서 로그아웃됐다.",
  "keywords": ["auth", "token", "bug"]
}
CREATE TABLE memory_candidates (
  id TEXT PRIMARY KEY,
  run_id TEXT NOT NULL REFERENCES runs(id),
  proposed_type TEXT NOT NULL CHECK (proposed_type IN (
    'task', 'code_pattern', 'problem', 'solution', 'project',
    'technology', 'error', 'fix', 'command', 'file_context',
    'workflow', 'general', 'conversation'
  )),
  title TEXT NOT NULL CHECK (length(trim(title)) BETWEEN 1 AND 200),
  content TEXT NOT NULL CHECK (length(trim(content)) > 0),
  keywords_json TEXT NOT NULL DEFAULT '[]' CHECK (json_valid(keywords_json)),
  status TEXT NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'promoted', 'rejected')),
  memory_ref TEXT,
  created_at TEXT NOT NULL,
  CHECK (
    (status IN ('pending', 'rejected') AND memory_ref IS NULL)
    OR
    (status = 'promoted'
      AND memory_ref IS NOT NULL AND length(trim(memory_ref)) > 0)
  )
);

CREATE INDEX memory_candidates_run_status_idx
  ON memory_candidates(run_id, status, created_at);

저장 도구가 id, status=pending, created_at을 자동으로 채우고 keywords 배열을 keywords_json으로 직렬화한다. id는 후보를 구분하는 고유 ID, created_at은 후보를 저장한 시각이다.

유지 원칙

DB, MemoryGraph, JSON이 같은 사실의 정본이 되지 않도록 역할을 분리한다.

작업 중에는 무엇을 기록하는가?
현재 문맥에서 실제로 알 수 있는 후보 하나를 발견 즉시 저장한다. 다른 후보가 생길 때까지 기다리거나 관계를 미리 판단하지 않는다.
후보 사이의 관계는 잃어버리지 않는가?
같은 작업에서 나온 후보는 run_id로 함께 조회할 수 있다. 종료 전 검토가 후보 내용과 기존 MemoryGraph 기억을 다시 읽고 최종 관계를 판단한다.
원본 출력과 로그는 어디에 두는가?
후보 테이블에는 복사하지 않고 Run Trace 또는 Artifact에서 찾는다. 후보 DB는 장기 기억 후보의 핵심 내용만 가볍게 보관한다.
JSON과 SQLite를 함께 수정해도 되는가?
안 된다. SQLite가 유일한 정본이고 JSON은 사람이 확인해야 할 때 DB에서 생성하는 내보내기다.
타입 목록은 어디에서 관리하는가?
MemoryGraph 기억 타입 목록은 저장 도구와 .harness/schema.sql이 같은 상수 정의에서 생성해야 한다. 관계 타입은 최종 검토와 MemoryGraph 저장 도구가 관리한다.

MemoryGraph와의 대응

이 스키마는 MemoryGraph MemorySchema와 RelationshipSchema에 맞추되, 하네스의 실행·검토 정보는 MemoryGraph에 불필요하게 복사하지 않는다.

후보 DB에서 이동

  • 기억: proposed_type, 제목, 내용, 키워드
  • 같은 Run의 후보는 run_id로 함께 조회
→

MemoryGraph 정본

  • 검토를 통과한 최종 기억 본문
  • 실제 기억 사이의 방향 있는 관계
  • 생성된 기억 ID와 필요한 경우 관계 ID

후보 DB에만 남는 정보: run_id와 처리 상태다. MemoryGraph 저장이 끝나면 반환된 ID만 memory_ref로 연결한다. 관계는 최종 노드와 기존 기억을 모두 확인한 뒤 MemoryGraph에 직접 저장한다.

기준: MemoryGraph main 브랜치 커밋 4f834c0.
