Design before implementation · 2026-08-29

MemoryGraph
저장 도구 설계

장기 기억 후보를 검토한 뒤 신규 저장·기존 기억 병합·관계 연결·후보 마감까지 안전하게 수행하는 도구의 경계와 생성 순서를 정한다. 모델은 판단하고, 도구는 검증된 계획을 기계적으로 실행한다.

Codex에는 읽기 도구 1개와 쓰기 도구 1개만 보여준다.

세부 MemoryGraph API와 두 SQLite DB 사이의 처리 순서는 Adapter 내부에 숨겨 호출 누락과 부분 실패를 줄인다.

01 · Boundary

판단과 실행을 분리한다

기억의 가치·중복·관계는 추론이 필요하다. 반면 타입 검증, DB 쓰기, 상태 전이와 재시도는 같은 입력이면 같은 결과를 내야 한다.

Skill

Memory Finalize Skill

pending 후보를 읽고 저장 가치, 중복 여부, 병합 내용, 관계를 판단한다. 최종 Storage Plan만 만든다.

MCP Adapter

harness-memory

Codex가 호출하는 얇은 입구다. 후보를 State DB에서 읽고 TypeScript 저장 모듈을 호출한 뒤 후보 상태까지 마감한다.

Deep Module

MemoryGraph Writer

MemoryGraph v0.13.0의 SQLiteBackend를 직접 사용한다. 입력 검증, 저장·병합, 관계 생성, 재시도 안전성을 내부에서 처리한다.

왜 MemoryGraph의 작은 함수를 MCP로 그대로 노출하지 않는가?

storeMemory, updateMemory, createRelationship, promote_candidate를 각각 호출하게 하면 Codex가 순서와 실패 복구를 매번 기억해야 한다. 하나의 깊은 쓰기 도구가 이 복잡성을 맡는다.

03 · Interface

최소 MCP 도구 계약

MCP 도구는 Codex가 이름·설명·입력 스키마를 보고 호출하는 함수다. 실제 DB 접근은 도구 서버 내부에서 수행한다.

Read

inspect_memory_candidate()

후보 한 건과 관련 기존 기억을 함께 반환한다. Finalize Skill이 신규 저장인지 병합인지, 어떤 관계가 가능한지 판단할 때 사용한다.

  • candidate_id: 검토할 후보의 고유 ID
  • extra_terms: 후보 자체 키워드에 선택적으로 보탤 짧은 검색어 배열
  • limit: 반환할 기존 기억 수, 기본 5·최대 10
Write

finalize_memory_candidate()

검토가 끝난 Storage Plan을 실행한다. 신규 저장·기존 기억 병합·관계 생성 후에만 후보를 promoted로 바꾸며, 제외 결정은 rejected로 마감한다.

  • candidate_id: 처리할 후보이자 재시도 식별자
  • decision: create, merge, reject
  • memory: 최종 기억 내용. merge일 때 완성된 결과 필수
  • relationships: 확정된 관계 목록

읽기 도구 예시

{
  "candidate_id": "MC-27f4",
  "extra_terms": ["pragma", "foreign key"],

    "keywords": ["sqlite", "foreign key"]
  },
  "matches": [
    {"id":"m-81","type":"problem","title":"FK 누락",
     "summary":"연결별 PRAGMA가 필요하다."}
  ],
  "warnings": []
}

04 · Failure policy

완전한 성공 뒤에만 승격한다

State DB와 MemoryGraph DB는 별도 SQLite 파일이므로 두 DB를 하나의 트랜잭션으로 묶을 수 없다. 따라서 도구는 작은 Saga처럼 순서와 재시도를 관리한다.

후보 선점·검증후보가 pending인지 확인하고, 한 후보의 Finalize를 동시에 두 번 실행하지 않도록 프로젝트 로컬 잠금을 잡는다.
입력 정규화공식 MemoryType·RelationshipType, 길이, 점수 범위, 관계 대상 존재 여부를 쓰기 전에 모두 검사한다.
노드 저장 또는 병합create는 candidate:<candidate_id>라는 결정적 ID를 사용한다. merge는 지정된 기존 노드만 갱신한다.
관계 생성같은 from + to + type 관계가 있으면 재생성하지 않고 skipped로 계산한다.
후보 상태 마감노드와 모든 관계가 성공한 뒤 memory_ref를 기록하고 promoted로 바꾼다. reject만 MemoryGraph 쓰기 없이 즉시 끝난다.
상황반환후보 상태다음 행동
전체 성공committedpromoted 또는 rejected종료
입력·타입·대상 오류conflictpendingSkill이 계획을 고쳐 다시 호출
노드는 저장됐지만 관계 일부 실패partialpending같은 candidate_id와 계획으로 재시도
MemoryGraph 성공 후 후보 승격 실패partialpending재호출 시 기존 노드·관계를 감지하고 승격만 재수행
이미 promoted/rejected 후보 재호출conflict 또는 동일 Receipt기존 상태 유지같은 결과면 안전 반환, 다른 계획이면 거부

삭제로 되돌리지 않는다

관계 실패를 이유로 이미 저장된 노드를 삭제하면 기존 관계나 다른 후보의 참조까지 잃을 수 있다. 후보를 pending으로 남기고 앞으로 재시도한다.

원문 로그를 넣지 않는다

도구 입력과 Receipt에는 정제된 기억, 개수, ID, 짧은 오류 코드만 둔다. 프롬프트 전문·명령 원본 출력·비밀정보는 저장하지 않는다.

05 · Modules

프로젝트 내부 배치

외부 인터페이스는 작게 유지하되, MemoryGraph 연결과 정책은 테스트 가능한 TypeScript 모듈로 분리한다.

src/harness/ ├── memory/ │ ├── types.ts # Tool 요청·Receipt와 내부 Port 타입 │ ├── client.ts # MemoryGraph 연결 생명주기 │ ├── recall.ts # 기존 작업 시작 Recall │ ├── inspect.ts # 후보 검색 결과를 작게 정리 │ ├── finalize.ts # 저장·병합·관계·재시도 정책을 가진 Deep Module │ └── cli.ts # Python Adapter가 JSON stdin으로 호출하는 Bridge ├── memory_mcp_server.py # Codex에 inspect/finalize 두 도구를 노출 └── state_store.py # 후보 조회·promote·reject 상태 함수 tests/ ├── memory/ # TypeScript 저장 정책·실제 SQLite 통합 테스트 └── test_memory_mcp_server.py # MCP 입력 검증·Bridge·상태 마감 테스트 .codex/config.toml # harness-memory MCP 서버 등록
Port

MemoryWriter

저장 모듈이 필요한 get/store/update/createRelation/getRelations만 정의한 내부 인터페이스다. 테스트에서는 가짜 구현으로 정책만 검증한다.

Adapter

SQLiteBackend

Port를 MemoryGraph v0.13.0 API에 연결하는 구현이다. 외부 라이브러리 세부 타입이 Finalize 정책 밖으로 새지 않게 한다.

Bridge

JSON stdin/stdout

Python MCP가 셸 문자열을 만들지 않고 Bun 프로세스에 JSON을 전달한다. stdout은 Receipt 한 줄만 사용하고 로그는 stderr로 분리한다.

06 · Build order

도구 생성 과정

구현은 계약부터 고정하고 안쪽으로 내려간다. 각 단계가 끝날 때 다음 단계가 의존할 테스트 표면이 생긴다.

요청·응답 계약 고정InspectRequest/Response, FinalizePlan, FinalizeReceipt와 허용값을 types.ts에 정의한다.
후보 단건 조회 함수 보강State Store가 candidate_id로 후보 하나를 읽게 한다. MCP에서 전체 후보 목록을 받아 다시 찾지 않는다.
MemoryWriter Port와 Adapter 구현MemoryGraph v0.13.0의 SQLiteBackend를 감싸고 공식 타입·관계 검증을 재사용한다.
Inspect Module 구현후보 키워드와 추가 검색어를 정규화하고 기존 Recall 병합 규칙을 재사용하되, 판단에 필요한 type·tags·summary를 반환한다.
Finalize Deep Module 구현create·merge·reject 분기, 결정적 ID, 관계 중복 검사, partial Receipt를 구현한다.
CLI Bridge 추가inspect와 finalize 명령은 JSON stdin을 받고 JSON stdout을 반환한다. 프로세스 종료 코드는 계약 오류와 운영 오류를 구분한다.
Python MCP Adapter 구현inspect_memory_candidate와 finalize_memory_candidate만 노출하고, State DB 후보 상태와 TypeScript Bridge를 조율한다.
Codex 설정 등록.codex/config.toml에 harness-memory 서버와 두 도구만 허용한다. PreToolUse는 inspect는 Run 없이 읽기 허용, finalize는 유효한 Run을 요구한다.
Finalize Skill 연결도구가 안정화된 뒤 별도 Skill에서 채점 기준과 호출 순서를 작성한다. 도구 구현과 LLM 판단 규칙을 한 번에 섞지 않는다.
07 · Verification

완료 기준

단순 성공 경로보다 중복 호출과 중간 실패가 안전한지가 중요하다.

검증 층반드시 확인할 사례완료 신호
계약 단위 테스트잘못된 decision·점수·타입·관계 방향·빈 candidate_id쓰기 전 명확한 오류 코드
Finalize 정책 테스트create, merge, reject, 같은 계획 재호출, 다른 계획 충돌동일 입력이 중복 노드·관계를 만들지 않음
부분 실패 테스트노드 성공 후 관계 실패, 그래프 성공 후 promote 실패후보 pending 유지, 재시도로 committed

후보 가치 점수표, Memory Finalize Skill의 상세 프롬프트, Stop Hook 재호출 정책, MemoryGraph 시각화 웹은 저장 도구가 검증된 뒤 별도 설계한다.

08 · Glossary

핵심 키워드

구현 중 같은 단어를 같은 의미로 사용하기 위한 짧은 사전이다.

Candidate
작업 중 발견했지만 아직 장기 기억으로 확정하지 않은 임시 기록.
Storage Plan
Skill이 만든 최종 실행 명세. create·merge·reject 결정과 완성된 기억·관계를 담는다.
Receipt
저장 도구의 실행 영수증. 실제 Memory ID, 관계 결과, 후보 상태와 경고를 담는다.
Deep Module
외부 함수는 적지만 내부에서 검증·저장 순서·복구 같은 많은 복잡성을 감추는 모듈.
Port
Finalize 정책이 저장 기술에 직접 묶이지 않도록 필요한 기능만 적은 내부 인터페이스.
Adapter
Port나 MCP 계약을 실제 MemoryGraph·SQLite·프로세스 호출에 연결하는 변환 계층.
Idempotency
같은 요청을 재실행해도 같은 노드나 관계가 중복 생성되지 않는 성질.
Partial
작업 일부만 성공한 상태. 후보는 pending으로 남고 같은 계획으로 이어서 재시도한다.
Saga
서로 다른 DB를 하나의 트랜잭션으로 묶지 못할 때, 단계별 성공 기록과 재시도로 전체 작업을 완성하는 방식.
memory_ref
State DB 후보가 실제 MemoryGraph 노드를 가리키는 문자열. 형식은 memorygraph:<memory_id>다.
