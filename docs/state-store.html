도메인 구조

하나의 저장소가 하나의 Project를 뜻하므로 Project는 DB 행이 아닌 암묵적인 범위다. 실제 저장 구조는 Feature와 WorkItem부터 시작한다.

프로젝트 작업은 WorkItem에서

Feature는 큰 목표나 작업 영역이다. 설계·조사·구현을 가리지 않고 목표·완료 조건·다음 행동을 가진 실제 작업 단위는 WorkItem이다.

Artifact는 Run에만 연결

WorkItem을 중복 저장하지 않는다. Artifact → Run → WorkItem 경로로 소속을 계산한다.

Evidence는 연결의 역할

별도 결과물이 아니다. Acceptance Criterion을 어떤 Artifact가 증명하는지 나타내는 연결이다.

WorkItem은 하위 WorkItem이나 별도 의존 관계를 갖지 않는 평평한 실행 단위다. 작업 순서는 status로 실행 가능 여부를 구분하고, next_action과 block_reason에 바로 다음 행동과 막힌 이유를 기록해 관리한다.

테이블을 선택하면 필드의 형식, 필수 여부와 쉬운 설명을 볼 수 있다. 검색은 테이블명·필드명·설명을 함께 찾는다.

상태 전이와 완료 판정

상태는 자유 문장이 아니라 허용된 길로만 이동한다. 잘못된 완료나 재사용된 Run을 기계적으로 막기 위한 규칙이다.

WorkItem 상태

backlog→ready→in_progress→done
in_progress→blocked→ready
현재갈 수 있는 다음 상태
backlogready, cancelled
readyin_progress, cancelled
in_progressready, blocked, done, cancelled
blockedready, cancelled
done없음
cancelled없음

blocked가 해제되면 바로 실행하지 않고 ready로 돌아가 현재 조건과 다음 행동을 다시 확인한다. cancelled는 모든 미완료 상태에서 갈 수 있다.

next_action은 backlog에서는 선택, ready·in_progress·blocked에서는 필수이며 done·cancelled에서는 비워 둔다.

Run 상태

running→succeeded
running→failed
running→interrupted
running→cancelled

끝난 Run을 다시 실행 중으로 바꾸지 않는다. 같은 WorkItem을 재시도하면 새 Run을 만든다. 동일한 WorkItem에는 running Run을 최대 하나만 허용한다. failed, interrupted, cancelled에는 termination_reason을 반드시 남긴다.

Run 종료와 WorkItem 상태 조합

작업 결과Run 상태WorkItem 상태
작업과 검증 완료succeededdone
이번 Run은 성공했고 전체 작업은 계속succeededready + 새 next_action
외부 조건에 막혀 중단interruptedblocked
실패했지만 다시 시도 가능failedready
세션 중단 후 다시 시도 가능interruptedready
작업 자체를 취소cancelledcancelled

finish_run()은 Run 종료, WorkItem 상태 변경과 각 State Event 기록을 하나의 SQLite 트랜잭션으로 처리한다. 일부만 성공할 수 없으며, 하나라도 실패하면 전체 변경을 되돌린다.

WorkItem을 done으로 바꾸기 전 확인

01

Acceptance Criterion이 하나 이상 존재하는가?

02

모든 조건이 passed 또는 waived인가?

03

passed 조건마다 같은 WorkItem에서 나온 유효한 Evidence가 있는가?

04

상태 변경 이유와 actor를 State Event에 남겼는가?

유효한 Evidence는 같은 WorkItem의 Run에서 생성되고 verification_status가 passed 또는 not_applicable인 Artifact다. pending과 failed Artifact만으로는 조건을 통과시킬 수 없다. 모든 Acceptance Criterion은 완료에 필요한 조건이며, complete_work_item()은 이 규칙을 DB에서 다시 확인하고 하나라도 충족하지 않으면 WorkItem을 done으로 바꾸지 않는다.

state.db와 runtime/bindings/는 로컬 작업 데이터라 Git에서 제외한다. Binding은 현재 Codex 세션이 어느 Run을 사용하는지 Hook에 알려 주는 임시 포인터이며 프로젝트 상태의 정본이 아니다. schema.sql은 재현 가능한 구조 정의이므로 Git으로 추적하고, exports/는 언제든 다시 만들 수 있는 파생물이다.

단일 DB 모듈과 SQLite 연결

v1에서는 DB 연결·조회·상태 변경·무결성 검사를 src/harness/state_store.py 한 파일에 모은다. SQLite의 외래키 검사는 연결마다 적용되므로, 이 파일의 모든 DB 함수는 공통 open_database()를 통해서만 DB를 연다.

src/harness/
  state_store.py        # 모든 DB 연결·조회·변경·검증 함수
  mcp_server.py         # Codex 도구를 state_store.py 함수에 연결
  runtime_binding.py    # 세션별 Binding 관리와 Run 소유자 확인

.harness/
  schema.sql            # 테이블·제약·인덱스·View 정의
  state.db              # 실제 로컬 상태 데이터
state_store.py

open_database(), WorkItem·Run·Artifact·Evidence·Memory Candidate의 생성과 조회, 상태 전이와 완료 검증 등 DB 관련 함수를 모두 담는 단일 내부 모듈이다.

mcp_server.py

Codex에 도구 이름과 입력 형식을 공개하고 대응하는 state_store.py 함수를 호출하는 얇은 연결부다. SQL과 상태 규칙을 중복 구현하지 않는다.

runtime_binding.py

.harness/runtime/bindings/<session-id>.json을 원자적으로 생성·조회·삭제하고 Run의 소유 세션을 찾는다. 세션 소유권을 WorkItem이나 Run 테이블에 중복 저장하지 않으며 Hook은 Binding과 DB의 실제 상태를 함께 확인한다.

분리 시점

v1에서는 파일을 미리 나누지 않는다. 실제 구현이 커져 한 파일의 탐색과 변경이 불편해질 때만 도메인별 모듈로 분리한다.

대표 DB 함수: open_database(), create_work_item(), start_run(), finish_run(), change_work_item_status(), create_artifact(), link_evidence(), pass_criterion(), complete_work_item(), create_candidate(). 각 함수는 SQL 실행뿐 아니라 자신이 변경하는 상태의 규칙도 함께 검사한다.

DB 경로 선택, SQLite 연결 생성, 외래키 활성화와 확인을 한곳에서 책임지는 state_store.py의 내부 공통 함수다.

직접 연결 금지

MCP 도구, CLI, Hook과 테스트는 각자 sqlite3.connect()를 호출하지 않는다. 모든 DB 작업은 state_store.py가 제공하는 함수를 재사용한다.

실패 시 중단

외래키 활성화 결과가 1이 아니면 연결을 반환하지 않고 오류로 중단한다. 관계 검사가 꺼진 채로 상태를 기록하는 것을 허용하지 않는다.

def open_database():
    db = sqlite3.connect(PROJECT_ROOT / ".harness" / "state.db")
    db.execute("PRAGMA foreign_keys = ON")

    enabled = db.execute("PRAGMA foreign_keys").fetchone()[0]
    if enabled != 1:
        db.close()
        raise RuntimeError("SQLite 외래키 활성화 실패")

    return db

schema.sql에 적힌 PRAGMA foreign_keys = ON만으로는 충분하지 않다. 그 명령은 스키마를 실행한 연결에만 적용되므로, 이후 create_candidate() 같은 MCP 도구가 새 연결을 만들 때도 반드시 open_database()를 거쳐야 한다.

헷갈리기 쉬운 원칙

설계가 커져도 동기화 비용과 중복 데이터를 늘리지 않기 위해 지켜야 할 핵심만 모았다.

Feature 진행률을 직접 저장하나?
아니다. 소속 WorkItem의 상태를 집계한다. Project의 완료·진행·막힘 수도 같은 방식으로 계산한다.
설계·조사 작업도 WorkItem과 Run을 사용하나?
그렇다. 프로젝트 목표를 진전시키고 결과나 다음 행동을 이후 세션에서 이어받아야 한다면 research 또는 decision WorkItem과 Run을 사용한다. 답변으로 끝나는 일회성 질문만 상태 저장소에 넣지 않는다.
적합한 WorkItem이 아직 없다면?
Codex가 독립적인 목표와 완료 조건을 가진 WorkItem을 즉시 만들 수 있다. 초기 설계처럼 Feature가 아직 없으면 feature_id를 비워 두며, 관련 기존 WorkItem이 있다면 새로 만들기보다 재사용한다.
WorkItem의 next_action은 언제 필요한가?
backlog에서는 없어도 되지만 대략적인 방향이 있다면 적을 수 있다. ready와 in_progress에는 지금 바로 할 행동을 반드시 적고, blocked에는 막힘을 해제하기 위한 행동을 적는다. done과 cancelled에서는 반드시 비워 둔다.
실행 중인 Run이 있는데 WorkItem 상태만 바꿀 수 있나?
안 된다. 정상적인 작업 종료는 finish_run()이 Run과 WorkItem을 함께 변경한다. 별도 change_work_item_status()는 해당 WorkItem에 running Run이 있으면 ready, blocked, done, cancelled로의 변경을 거부한다.
여러 Codex 세션이 동시에 작업할 수 있나?
서로 다른 WorkItem은 세션별 Binding과 Run을 사용해 병렬 실행할 수 있다. 같은 WorkItem에는 DB가 running Run을 하나만 허용하므로 먼저 시작한 세션만 작업한다. 다른 세션은 새 Run이나 Binding을 만들지 않고 원래 세션에서 이어서 작업하라는 안내를 받는다.
다른 세션이 비정상 종료돼 WorkItem이 잠기면?
시간 만료나 자동 takeover로 추측하지 않는다. Codex가 충돌을 설명하고 “해당 세션이 이미 종료됐다면, 남은 Run을 interrupted로 종료하고 WI 잠금을 해제할까요?”라고 묻는다. 사용자가 명시적으로 동의하면 recover_abandoned_work(work_item_id, expected_run_id)가 조회 당시의 정확한 Run만 중단 처리하고 WorkItem을 기존 next_action이 있는 ready로 원자적으로 되돌린다. 이는 기존 Run의 정상 성공 종료나 재개가 아니다. 이후 현재 세션의 새 Run은 start_work()로 별도 생성한다.
실패하거나 아직 검증 중인 Artifact도 완료 근거가 되나?
안 된다. pass_criterion()은 같은 WorkItem에서 나온 Evidence 중 verification_status가 passed 또는 not_applicable인 Artifact가 하나 이상 있을 때만 조건을 passed로 바꾼다. 과거의 실패 Artifact가 남아 있어도 별도의 유효한 Artifact가 있으면 통과할 수 있다.
Run 요약에 전체 작업 과정을 적나?
아니다. 다음 Run이 이어서 일할 수 있는 짧은 결과만 적는다. 상세 도구 호출과 원본 출력은 trace_ref가 가리키는 Trace에서 찾는다.
성공한 Run 뒤에도 WorkItem을 계속할 수 있나?
가능하다. finish_work(outcome="progressed")를 사용하면 Run은 succeeded로 끝나고 WorkItem은 새 next_action이 있는 ready로 돌아간다. WorkItem 전체가 끝났을 때만 completed로 done 처리한다.
장기 기억 후보의 관계는 어디에 적나?
후보 DB에는 적지 않는다. 같은 Run의 후보는 run_id로 함께 찾고, 종료 전 검토가 기존 MemoryGraph 기억까지 비교해 실제 관계만 MemoryGraph에 직접 저장한다.
State Event와 Trace는 같은가?
다르다. State Event는 상태가 언제 왜 바뀌었는지 남기는 작은 감사 기록이고, Trace는 한 Run 안의 모델·도구 호출을 담는 상세 실행 기록이다.

핵심: SQLite는 현재 상태, 변경 이력과 검토 전 기억 후보의 정본이다. 문서는 구조를 설명하고, Git과 Artifact는 결과를 증명하며, Trace는 실행을 기록하고, MemoryGraph는 검토를 통과한 이유와 경험을 보존한다.
