MemoryGraph의 기본 스키마와 확장 범위

사용자가 저장하는 핵심 대상은 하나의 Memory 노드다. 문제와 해결책은 서로 다른 구조가 아니라 Memory.type으로 구분되며, 기억 사이에는 미리 정의된 방향 관계를 연결한다.

1핵심 사용자 노드 라벨
13허용된 기억 타입
35허용된 관계 타입

먼저 이것만 알면 된다

MemoryGraph를 사용할 때 가장 자주 혼동하는 “노드 종류”와 “기억 분류”를 분리하면 전체 구조가 단순해진다.

1
핵심 노드는 모두 Memory

일반 사용자가 직접 저장하는 기억은 동일한 구조의 Memory 노드다.

2
문제·해결책은 type 값

problem과 solution은 별도 노드 라벨이 아니라 분류값이다.

3
관계는 방향이 있다

solution —SOLVES→ problem처럼 출발점과 도착점에 의미가 있다.

4
임의 타입은 바로 추가할 수 없다

공식 목록 밖의 값은 거부되며, 확장하려면 소스를 수정하고 다시 빌드해야 한다.

하나의 구조, 다른 분류

두 기억은 모두 Memory다. type 값과 관계만 달라진다. 점선으로 표시한 Entity와 Outcome은 고급 기능이 만드는 내부 보조 구조다.

용어 바로잡기

노드
그래프에 저장되는 대상 하나. 문제 기억 하나가 노드 하나다.
노드 라벨
노드의 구조적 종류. 일반 기억은 Memory 라벨을 쓴다.
Memory.type
기억이 문제인지 해결책인지 나타내는 분류 필드다.
관계
두 노드가 어떻게 연결되는지 나타내는 방향 있는 선이다.
enum
프로그램이 허용하는 값을 미리 정해 둔 목록이다.
(Memory { type: "problem", ... })
(Memory { type: "solution", ... })

새 종류를 추가할 수 있는가?

가능하지만 설정이나 CLI에서 즉석 등록하는 방식은 아니다. 변경 범위에 따라 비용이 크게 달라진다.

HARNESS v1 권장

기존 type + tags

공식 Memory.type을 큰 분류로 사용하고, 우리만의 세부 분류는 tags로 표현한다.

  • 공식 CLI와 바로 호환
  • 소스 포크와 재빌드 불필요
  • 사용 사례가 쌓인 뒤 확장 여부 판단 가능
필요성이 입증된 뒤

MemoryGraph 소스 확장

MemoryType이나 RelationshipType enum을 수정하고 다시 빌드한다. 새 노드 라벨은 더 넓은 변경이 필요하다.

  • 모델과 검증 로직 수정
  • 저장·검색 및 CLI/API 수정
  • 각 데이터베이스 백엔드 대응
왜 임의 값을 바로 넣을 수 없나?

store_memory는 공식 목록 밖의 기억 타입을 Invalid memory type으로 거부하고, create_relationship도 공식 목록 밖의 관계 타입을 Invalid relationship type으로 거부한다.

완전히 새로운 노드 라벨은?

타입 목록만 수정해서는 부족하다. 새로운 모델과 저장·검색 경로, CLI/API, 각 DB 백엔드까지 확장해야 한다. 현재 공식 CLI에는 임의 노드 라벨 생성이나 범용 Cypher 실행 명령이 없다.
