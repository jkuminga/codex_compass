PreToolUse 구현 설계

모든 Codex 도구 호출 직전에 “그냥 읽는가, 현재 Run의 프로젝트 작업인가, 절대로 실행하면 안 되는가”를 기계적으로 판별한다. 이 문서는 docs/single-request-pipeline.html의 정책을 실제 구현 단위로 좁힌 임시 정본이다.

구조 결론판별 순서apply_patchBashMCPBinding구현 구조테스트위험

도구별 Hook을 여러 개 만들까?

설정과 실행 코드를 분리해서 생각한다.

입구는 하나, 판별기는 도구군별로.

PreToolUse는 matcher를 두지 않은 하나의 Hook으로 모든 도구를 받아야 한다. 내부 Dispatcher가 apply_patch, Bash 실행, Harness MCP, 외부 MCP, 미등록 로컬 도구로 나누어 같은 정책 엔진에서 판정한다.

single hook processexternal MCP = pass throughglobal hooks = out of scopeunknown local = run required

왜 좁은 matcher를 쓰지 않나?

알고 있는 도구에만 matcher를 달면 새 로컬 도구나 이름이 바뀐 Harness 도구가 Hook 자체를 통과하는 구멍이 생긴다. PostToolUse는 start_work·finish_work만 후처리하면 되므로 좁은 matcher가 맞지만, PreToolUse는 모든 호출을 받은 뒤 외부 MCP만 의도적으로 통과시킨다.

전역 Hook과의 충돌은 판단하지 않는다.

이 프로젝트의 PreToolUse는 .codex/hooks.json에 정의된 자신의 입력과 정책만 책임진다. ~/.codex/hooks.json의 전역 Hook을 탐지·해석·비활성화하거나 실행 순서를 조정하지 않는다. 전역 Hook은 사용자가 설치한 Codex·Orca 같은 외부 도구의 책임 영역이며, 충돌이 생기면 해당 도구 또는 사용자가 전역 설정에서 해결한다.

확인 근거: 현재 프로젝트 PostToolUse는 matcher로 두 MCP만 고르고 내부에서 다시 분기한다. 사용자 전역 Codex 설정에는 matcher 없는 PreToolUse가 등록되어 있어 모든 도구를 받는 구성이 가능하다. 공식 OpenAI 공개 문서 검색에서는 현재 Hook 입출력 스키마 전용 페이지를 확인하지 못했으므로, 실제 구현 전 입력 캡처 테스트로 필드명과 deny 반환 형식을 고정한다.

최종 판별 순서

위험 검사가 항상 먼저다. 활성 Run은 위험 명령의 면허가 아니다.

1. 위험

Run 여부보다 먼저 찾아 무조건 거부한다.

2. Run 없이 통과

확실한 조회, 최소 작업 준비와 외부 MCP는 Binding 검사 없이 통과한다.

3. 작업 준비

WorkItem과 Run을 만들기 위한 일부 MCP만 예외로 허용한다.

4. 기본값

로컬 변경·복합 Bash·미등록 Harness 호출은 현재 Turn의 활성 Run을 요구한다.

apply_patch

패치 내용은 읽어서 안전성을 추론하지 않는다.

고정 분류: 프로젝트 변경

apply_patch는 파일을 만들거나 수정하거나 삭제할 수 있으므로 언제나 ACTIVE RUN REQUIRED다. 빈 패치처럼 실제 변화가 없을 가능성이 있어도 호출 전에는 구분하지 않는다.

추가 경로 차단

활성 Run이 있어도 저장소 밖 경로, .git/, .harness/state.db*, Binding 파일 같은 보호 경로의 직접 변경은 거부한다. 상태 DB와 Binding은 전용 함수만 사용한다.

Bash · exec_command

tool_input.cmd를 실행하지 않고 문자열과 토큰만 검사한다.

등급예시판정구현 규칙

DENYrm -rf, 모든 git reset, git clean, git push --force, 보호 경로 직접 변경Run이 있어도 거부원시 문자열과 토큰화 결과를 모두 검사하며 복합 명령 안에서도 가장 먼저 적용한다.
중요: rg 'a|b'의 정규식처럼 따옴표 안에 있는 문자는 셸 파이프로 보지 않는다. 반대로 rg foo | head의 파이프는 복합 호출이다. v1 파서는 완전한 셸 실행기가 아니라 따옴표와 escape를 구분하는 작은 Lexer다.

활성 Run 검증

변경 가능 호출에서만 SQLite를 연다.

validate_active_binding(
  session_id = event.session_id,
  current_turn_id = event.turn_id
)

1. bindings/<session_id>.json 존재
2. binding.turn_id == current_turn_id
3. binding.run_id ↔ binding.work_item_id 일치
4. DB Run.status == "running"
5. DB WorkItem.status == "in_progress"

모두 참 → allow
하나라도 실패 → deny

왜 Binding 파일만 보지 않나?

Binding은 현재 Codex Turn이 어떤 Run을 쓰는지 알려주는 빠른 포인터다. 실제 상태의 정본은 SQLite이므로 파일이 오래됐거나 조작됐을 수 있다. validate_active_binding()은 둘을 교차 확인하는 기존 함수다.

조회 전용 호출은 이 검사를 하지 않으므로 매 도구 호출마다 DB를 여는 비용은 발생하지 않는다.

정책 결과 객체

ToolDecision은 Hook 내부에서 쓰는 작은 판정 결과다.

  • classification: read, bootstrap, run_required, dangerous
  • allowed: 실행 허용 여부
  • reason_code: 테스트 가능한 짧은 코드
  • message: Codex와 사용자가 이해할 쉬운 설명

실제 Codex deny JSON 필드명은 구현 전 Hook 입력·출력 캡처 테스트로 확인하고 Adapter에서만 매핑한다.

정책표의 각 행을 양성·음성 사례로 고정한다.

통합 테스트 핵심: Run 없이 읽기는 계속 가능해야 하고, Run 없이 변경은 도구 실행 전에 멈춰야 하며, start_work PostToolUse가 Binding을 만든 직후 동일 Turn의 변경 호출은 통과해야 한다.

실제 Codex 검증 결과와 보완

Codex CLI 0.149.1은 원래 Hook의 일반 실패를 fail-open으로 처리한다. 이를 보완하기 위해 pre_tool_use_guard.py 감시 래퍼를 추가했고, 자식 정책 Hook의 실패를 Codex 공식 차단 신호인 종료 코드 2로 변환한다.

  1. 명시적 deny: 차단됨
  2. 자식 Hook 종료 코드 1: 래퍼가 종료 코드 2로 변환해 차단
  3. 잘못된 출력 JSON: 래퍼가 검증 실패로 차단
  4. 자식 Hook 내부 제한 시간 초과: 래퍼가 자식을 종료하고 차단

확정된 감시 래퍼 규칙

감시 래퍼: 실제 정책 Hook을 자식 프로세스로 실행하고, 정상적인 allow·deny JSON만 Codex에 전달하는 얇은 보호 계층이다.

  • Codex의 바깥쪽 Hook 제한 시간은 10초, 래퍼의 자식 제한 시간은 7초로 둔다.
  • 자식이 정상 종료하고 PreToolUse의 allow·deny JSON 계약을 만족할 때만 출력을 전달한다.
  • 자식 시작 실패, 비정상 종료, 잘못된 JSON, 잘못된 응답 구조, 내부 시간 초과는 stderr 사유와 종료 코드 2로 변환한다.
  • DB 오류는 조회 호출에는 영향을 주지 않되, 변경 호출에서는 deny로 바꾼다.
  • 사용자 결정에 따라 감시 래퍼 프로세스 자체가 강제 종료되는 경우는 v1 실패 범위에서 제외한다.

위험과 비범위

이 Hook을 완전한 셸 보안 장치로 오해하지 않는다.

위험대응v1에서 하지 않는 것
셸 문법 오판작은 Lexer, 좁은 조회 목록, 복합문은 Run 필요완전한 Bash AST 실행·효과 추론
새 로컬·Harness 도구의 Hook 우회matcher 없는 단일 PreToolUse와 미등록 기본 정책. 외부 MCP는 분류 후 의도적으로 통과도구 이름을 모델이 의미로 분류
위험 명령 우회위험 검사를 첫 단계로 두고 중첩 문자열도 검사사용자 승인만으로 위험 명령 허용
DB 조회 비용조회·준비 호출에는 Binding 검증을 생략모든 도구마다 프로젝트 전체 상태 조회
Hook이 보지 못하는 스크립트 내부 효과스크립트 실행은 Run 필요, Codex 샌드박스와 기존 권한 정책 병행PreToolUse를 OS 보안 경계로 간주
전역 Hook과 프로젝트 Hook의 동시 실행프로젝트 Hook은 자신의 판정만 독립적으로 수행하고 다른 Hook의 실행 순서나 결과에 의존하지 않음전역 Hook 탐지·충돌 판정·비활성화·조정
Harness v2 · 긴급 구현 설계 · 구현 완료 후 고유한 결정은 single-request-pipeline.html에 통합하고 이 임시 문서는 제거 여부를 검토한다.
