Harness v2 · State Store design

Run Tool Events · Artifact 스키마

PostToolUse가 받은 실행 사실을 가볍게 기록하고, 작업 종료 시 필요한 기록만 Artifact와 Acceptance Criterion의 Evidence로 승격하는 계약이다. 목표는 토큰을 더 쓰지 않으면서도 “무슨 도구가 실행됐는지”를 잃지 않는 것이다.

2핵심 테이블
0LLM 호출이 필요한 Hook 단계
결정 요약 전체 흐름 run_tool_events artifacts 마이그레이션 점검 후보 처리 계약 위험과 범위 구현 체크리스트

결정 요약

이번 설계에서는 OpenTelemetry를 새로 도입하지 않는다. 로컬 SQLite 상태 저장소에 PostToolUse의 짧고 안전한 실행 이벤트만 저장하고, 실제 Artifact 판정은 $work-finish 시점에 저비용 서브에이전트가 맡는다.

한 줄 결론PostToolUse는 사실을 기록하고, work-finish는 그 사실을 해석한다. artifacts.uri는 신뢰성의 필수 조건이 아니므로 nullable(값이 없어도 되는 선택 필드)로 둔다.

Hook이 하는 일 기계적

활성 Run을 찾고, 도구명·성공 여부·짧은 입력/결과 요약을 run_tool_events에 저장한다. 모델 재호출, MCP 호출, 전체 stdout 저장은 하지 않는다.

work-finish가 하는 일 추론

해당 Run의 pending 이벤트와 Acceptance Criteria(완료 조건)를 저비용 서브에이전트에 전달한다. 반환된 후보를 검증한 뒤 Artifact를 만들고, 필요한 경우 Evidence를 연결한다.

전체 데이터 흐름

이 흐름에서 이벤트와 Artifact는 같은 데이터를 무조건 두 번 저장하는 구조가 아니다. 이벤트는 원본 실행 사실이고, Artifact는 나중에 확인할 가치가 있다고 판정된 결과다.

run_tool_events — 실행 사실 테이블

이벤트(event)는 “어떤 Run에서 어떤 도구가 실행됐고 성공했는가”를 남기는 내부 기록이다. 나중에 Artifact가 되지 않아도 보존할 수 있다.

필드설명값 규칙
idDB가 부여하는 이벤트 IDEVT-...; Artifact의 source_event_id가 가리키는 기준 ID
tool_use_idCodex가 한 도구 호출에 붙인 식별자UNIQUE(run_id, tool_use_id)로 중복 Hook 저장 방지
run_id이 실행이 속한 RunRuntime Binding으로 찾은 활성 Run
tool_name실제로 호출된 도구 이름bash, apply_patch, MCP 도구 등
tool_family도구의 큰 분류bash · file_edit · mcp · lifecycle · other
status도구 실행 결과succeeded · failed · unknown
exit_code셸 명령의 종료 코드Bash가 아니면 NULL
input_summary입력의 짧고 비밀정보가 제거된 요약전체 프롬프트·환경변수·파일 내용 저장 금지
result_summary결과의 짧은 요약stdout/stderr 전체가 아니라 길이 제한 요약만 저장
review_statusArtifact 검토 상태pending · promoted · ignored · error
created_at이벤트 저장 시각UTC timestamp
URI를 이벤트에 강제로 넣지 않는다PostToolUse의 공통 입력에는 도구명·입력·결과는 있지만, “이 결과가 코드베이스의 어느 파일/커밋인가”를 항상 안정적으로 계산할 수 있는 URI는 없다. 그래서 v1 이벤트 스키마에는 reference_uri를 두지 않는다.
UNIQUE(run_id, tool_use_id)
-- 같은 도구 호출이 Hook 재시도로 두 번 들어와도 한 번만 보관

artifacts — 확인할 가치가 있는 결과

Artifact는 테스트, 린트, 빌드, 커밋, 파일 변경처럼 나중에 결과를 확인할 만한 기록이다. 모든 이벤트가 Artifact가 되는 것은 아니다.

필드설명값 규칙
idArtifact IDEvidence가 연결할 내부 ID
run_id어느 Run의 결과인지필수
source_event_id자동 승격의 원본 이벤트 ID자동 등록이면 run_tool_events.id; 수동 기록이면 NULL
kind결과 종류file · commit · test_run · lint_run · build_run · pull_request · deployment · screenshot · report · other
uri optional파일 경로, 커밋 SHA, 보고서 위치 등 사람이 다시 찾아갈 주소알 때만 저장. 모르면 NULL; 저장 여부가 AC 완료 조건은 아님
verification_status결과의 검증 상태not_applicable · pending · passed · failed
summary사람이 읽을 짧은 설명원본 출력·비밀정보를 넣지 않음
created_atArtifact 생성 시각UTC timestamp
source_event_id가 중복 방지의 기준source_event_id는 외부 호출 ID인 tool_use_id가 아니라 내부 run_tool_events.id다. 따라서 “이 이벤트가 이미 Artifact로 승격됐는가?”를 안정적으로 확인할 수 있다.
UNIQUE(run_id, kind, source_event_id)
-- source_event_id가 있는 자동 Artifact에 적용
-- source_event_id가 NULL인 수동 Artifact는 별도 허용

현재 코드·DB 마이그레이션 점검

설계는 적용 가능하지만, schema.sql만 바꾸고 기존 DB를 다시 초기화하는 방식으로는 충분하지 않다. SQLite는 기존 컬럼의 NOT NULL 제약을 단순히 완화하지 못하므로 명시적인 테이블 마이그레이션이 필요하다.

현재 판단: 데이터는 안전하게 옮길 수 있지만, 직접 적용은 금지현재 상태 DB에는 Artifact 210개가 있고 URI가 비어 있는 행은 없으며, 기존 중복 키도 없다. 따라서 기존 값을 보존하는 테이블 재생성 마이그레이션을 만들고 테스트한 뒤 적용한다.
점검 항목현재 상태판단
기존 Artifact 수210개기존 URI를 그대로 복사할 수 있음
기존 uri IS NULL0개nullable 전환 시 데이터 손실 위험이 낮음
기존 (run_id, kind, uri) 중복없음새 중복 정책으로 옮길 때 충돌 없음
run_tool_events 테이블아직 없음새 테이블·인덱스를 생성해야 함
현재 Python APIuri 필수uri: str | None과 source_event_id 지원 필요

기존 DB에 적용하는 순서

  1. run_tool_events 테이블과 UNIQUE(run_id, tool_use_id)를 먼저 만든다.
  2. 새로운 nullable uri와 source_event_id를 가진 artifacts_new 테이블을 만든다.
  3. 기존 artifacts의 모든 행을 새 테이블로 복사한다. 기존 URI는 그대로 보존한다.
  4. 외래키·트리거·인덱스를 확인한 뒤 기존 테이블을 교체하고 새 이름을 artifacts로 확정한다.
  5. PRAGMA foreign_key_check와 스키마 검사를 실행하고 커밋한다.

테이블 교체는 SQLite 외래키와 연결된 criterion_evidence를 함께 고려해야 한다. 구현 시 마이그레이션 전체를 하나의 안전한 절차로 감싸고, 실패하면 원래 테이블을 복구할 수 있어야 한다.

코드에서 함께 바꿀 것

  • state_store._validate_artifact_uri()가 None을 허용
  • create_artifact()에 선택 URI·source_event_id 추가
  • MCP record_artifact() 입력 스키마 변경
  • _REQUIRED_TABLES에 run_tool_events 추가

검증해야 할 것

  • 신규 DB와 기존 DB 모두 초기화
  • URI 없는 Artifact 생성
  • 이벤트 ID가 존재하지 않을 때 거부
  • 같은 이벤트의 Artifact 중복 저장 방지
  • Evidence·AC 완료 트리거가 그대로 동작하는지 확인
문서 동기화 필요state-store.html과 single-request-pipeline.html에는 아직 artifacts.uri가 필수이고 UNIQUE(run_id, kind, uri)를 쓴다는 설명이 남아 있다. 구현과 함께 nullable URI·source_event_id 기준으로 갱신한다.

work-finish 처리 계약

서브에이전트는 이벤트를 보고 “후보”를 반환한다. 실제 DB 쓰기는 메인 모델과 MCP/DB 함수가 담당해, 잘못된 ID나 허용되지 않은 상태가 저장되지 않게 한다.

단계주체입력 → 출력
1. 이벤트 수집PostToolUse HookCodex Hook payload → 유효한 Run에 compact run_tool_events 행 저장. Run이 없으면 도구를 막지 않고 건너뜀.
2. 후보 판단저비용 서브에이전트pending 이벤트 + AC 목록 → Artifact 후보와 Evidence 후보 JSON. 코드베이스 재탐색은 하지 않음.
3. 기계 검증메인 모델 / MCPevent ID, criterion ID, enum, 중복 여부를 확인 → 유효한 후보만 저장 함수에 전달.
4. Artifact 생성record_artifact()필요한 경우에만 Artifact 생성. uri 누락은 허용하고 source_event_id로 원본 이벤트 연결.
5. Evidence 연결verify_criterion()Artifact ID + AC ID → 해당 Artifact가 어떤 완료 조건을 증명하는지 연결.
6. 종료 재검사finish_work()postflight를 다시 읽고 pending 후보/필수 Evidence 규칙을 확인한 뒤 Run을 종료.
 
{
  "artifacts": [
    {
      "source_event_id": "EVT-a1b2c3",
      "kind": "test_run",
      "verification_status": "passed",
      "uri": null,
      "summary": "pytest 42개 통과"
    }
  ],
  "evidence": [
    {
      "source_event_id": "EVT-a1b2c3",
      "criterion_id": "AC-07",
      "note": "테스트 결과가 해당 완료 조건을 검증함"
    }
  ]
}

위 JSON은 서브에이전트의 후보 출력 예시다. 실제 Evidence 저장에는 먼저 Artifact를 생성해 얻은 artifact_id가 사용된다.

신뢰성·비용·범위

위험판단완화책
Hook가 매 도구마다 모델을 호출함비용과 지연이 커짐Hook는 요약·저장만 수행하고 LLM/MCP 호출을 하지 않는다.
URI를 채우기 위해 코드베이스를 다시 탐색함Artifact 판정 비용이 커짐uri는 optional. 알고 있는 경우에만 기록한다.
같은 이벤트가 두 번 Artifact가 됨중복 기록과 AC 판단 혼란source_event_id와 partial unique index로 자동 승격을 멱등 처리한다.
전체 출력에 비밀정보가 섞임보안·저장량 문제요약은 길이 제한·민감정보 제거 후 저장한다. 원문 stdout/stderr는 저장하지 않는다.
이벤트는 남았지만 Artifact가 되지 않음정상적인 선별 결과review_status=ignored를 남기고, AC 완료에는 검증된 Artifact/Evidence만 사용한다.

이번 범위에 없음

OpenTelemetry Collector, 별도 trace backend, 원격 관측 시스템은 도입하지 않는다.

이번 범위에 없음

모든 도구 결과를 Artifact로 저장하지 않는다. 이벤트와 검증 가능한 결과를 구분한다.

이번 범위에 없음

URI가 없다는 이유만으로 Artifact를 거부하거나 Codex가 파일을 다시 검색하도록 강제하지 않는다.

구현 체크리스트

  • run_tool_events 테이블·인덱스·UNIQUE(run_id, tool_use_id) 추가
  • 기존 artifacts를 보존하면서 nullable URI와 source_event_id로 교체하는 SQLite 마이그레이션 구현
  • PostToolUse 공통 payload에서 tool_input.command와 기존 샘플의 cmd를 모두 읽는 요약기 구현
  • Runtime Binding에서 활성 run_id를 찾지 못하면 저장을 건너뛰되 도구 실행은 차단하지 않기
  • artifacts.uri를 nullable로 마이그레이션하고, source_event_id와 자동 승격 중복 방지 인덱스 추가
  • 서브에이전트 출력의 이벤트 ID·AC ID·enum을 메인 경로에서 검증
  • Artifact 생성 후 실제 artifact_id로 Evidence 연결, 마지막에 finish_work() postflight 재검사
  • 요약 길이 제한·민감정보 제거·중복 Hook 재시도 테스트 추가
Harness v2 · 설계 기준 문서 다음 구현에서 스키마와 Hook 계약을 이 문서에 맞춘다.
