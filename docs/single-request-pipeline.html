단일 Codex 요청 파이프라인

한 번의 사용자 요청을 상태 조회, WorkItem 실행, 검증, 장기 기억 후보와 종료까지 연결하는 기준 흐름이다. Hook·Codex MCP·Skill은 서로 대신하지 않고 각자 잘하는 일만 맡는다.

핵심 규칙

Hook은 Run을 자동 생성·종료하지 않는다. Codex가 의미를 판단해 MCP로 시작하고 종료하며, Hook은 문맥 공급·기계적 기록·누락 검사만 한다.

구현됨

1. UserPromptSubmit

상태 DB를 읽고 실행 중인 WorkItem과 ready 후보 최대 3개를 짧게 주입한다. 사용자가 WorkItem ID를 적었다고 가정하지 않으며, Hook은 선택이나 Run 생성을 하지 않는다.

판단 책임을 나눈다

입력만 보면 답이 정해지는 처리는 Hook, 사용자 의도와 의미를 읽어야 하는 처리는 Codex, 반복되는 고급 추론 절차는 Skill이 맡는다.

Hook → state_store.py

모델 없이 가능한 기계 처리.

  • DB 건강 검사와 상태 조회
  • Binding이 가리키는 Run·정책·권한 확인
  • Trace와 식별 가능한 Artifact 기록
  • 종료 누락 검사와 1회 continuation

Codex → MCP

문맥과 결과 의미가 필요한 판단.

  • 일회성 답변과 프로젝트 작업 구분
  • 기존 WorkItem 재사용 또는 새 목표 생성
  • Run 시작과 최종 outcome 결정
  • Artifact와 완료 조건 연결
  • Run 요약과 next_action 작성

Codex → Skill

재사용하는 추론 절차.

  • 후보 가치 평가
  • 기존 기억 검색과 중복 판단
  • 관계 선택과 MemoryGraph 저장
  • 후보 promote 또는 reject

Hook이 현재 Run을 찾는 방법

DB에 Codex 세션 필드를 넣지 않고, 짧게 살아 있는 Runtime Binding을 별도로 둔다.

Runtime Binding

Codex thread 또는 Hook 식별자를 현재 WorkItem·Run과 연결하는 임시 포인터다. 프로젝트 상태의 정본은 아니며 실제 상태는 항상 SQLite에서 다시 확인한다.

  • PostToolUse가 성공한 start_work 결과의 ID를 받아 생성
  • Pre/PostToolUse와 Stop이 현재 Run 탐색에 사용
  • finish_work 성공을 본 PostToolUse가 삭제 또는 비활성화
  • 유실 시 DB의 running Run 후보를 찾되, 하나로 확정할 수 없으면 Codex에 재선택을 요구
.harness/runtime/
  <codex-thread-id>.json

{
  "work_item_id": "WI-123",
  "run_id": "RUN-456",
  "updated_at": "2026-08-13T08:00:00Z"
}

정본이 아니다. Hook은 Binding에서 ID를 찾은 다음 반드시 state_store.py로 실제 WorkItem과 Run 상태를 확인한다. 이 Binding과 Hook 어댑터는 아직 구현 전이다.

실패와 예외 처리

Hook이 결과 의미를 추측해 상태를 자동 마감하지 않는 것이 공통 원칙이다.

활성 Run 없이 파일을 수정하려 하면?
설계 문서를 포함한 저장소 변경은 프로젝트 작업이므로 먼저 WorkItem을 선택하거나 만들고 start_work를 호출해야 한다. PreToolUse는 Run 없는 변경 도구를 차단할 수 있다. 단순 질문과 프로젝트 조사 모두 읽기 도구를 쓸 수 있으므로, 읽기 전용 작업의 Run 필요 여부는 Codex가 AGENTS 지침에 따라 분류한다.
어떤 기존 WorkItem을 선택하나?
기본값은 재사용이다. “기존 WorkItem을 완료하려면 이번 요청도 처리해야 하는가?”가 참이면 같은 WorkItem에 새 Run을 만든다. 독립적으로 완료할 별도 목표와 완료 조건이 필요할 때만 새 WorkItem을 만든다.
후보 세 개와 맞는 WorkItem이 없다면?
세 항목은 정답이 아니라 빠른 후보다. 추가 상태 조회나 향후 검색 Interface로 관련 미완료 WorkItem을 확인하고, 그래도 적합한 목표가 없을 때 새 WorkItem을 만든다.
테스트는 통과했지만 Criterion과 연결되지 않았다면?
PostToolUse는 Artifact까지만 만든다. Codex가 verify_criterion으로 Evidence를 연결하지 않으면 Stop Guard가 누락을 알리고 한 번 계속한다.
작업이 실패하거나 막혔다면?
Codex가 finish_work에서 retry_needed, blocked 또는 interrupted를 선택하고 다음 Run이 이어갈 next_action과 종료 이유를 기록한다.
이번 Run은 성공했지만 WorkItem은 아직 남았다면?
finish_work(outcome="progressed")로 종료한다. Run은 succeeded, WorkItem은 ready와 새 next_action으로 남아 다음 Run에서 이어진다.
pending 기억 후보가 남았다면?
Memory Finalize Skill이 구현된 뒤에는 저장 또는 reject가 끝나지 않은 후보를 Stop Guard가 알리고 한 번 continuation을 요청한다. Skill 구현 전에는 경고만 한다.
한 번 더 실행해도 정리하지 못했다면?
무한 반복하지 않는다. 같은 이유의 재시도는 한 번으로 제한하고 Run을 보존한 채 남은 누락과 사용자 조치 필요성을 보고한다.
