단일 Codex 요청 파이프라인

한 번의 사용자 요청을 상태 조회, WorkItem 실행, 검증, 장기 기억 후보와 종료까지 연결하는 기준 흐름이다. Hook·Codex MCP·Skill은 서로 대신하지 않고 각자 잘하는 일만 맡는다.

핵심 규칙

Hook은 Run을 자동 생성하거나 성공으로 마감하지 않는다. 단, UserPromptSubmit은 현재 세션의 이전 turn에서 남은 것이 확실한 Run만 interrupted로 기계적으로 복구한다. Codex는 의미를 판단해 MCP로 새 Run을 시작하고 정상 결과를 종료한다.

현재 구현 상태

이 문서는 목표 파이프라인의 정본이다. 이미 동작하는 부분과 다음에 구현할 부분을 구분한다.

UserPromptSubmit, $work-start 스킬, SQLite·MCP, 세션별 Runtime Binding, start_work·finish_work 전용 PostToolUse와 Recall Wrapper.

사용자 프롬프트가 제출되면 모델보다 먼저 실행되는 Hook이다. 이전 turn에서 확실히 남은 Run만 기계적으로 복구한 뒤, 의미를 판단하지 않고 작은 State Context Packet을 Codex 문맥에 추가한다.

State Context Packet

이번 요청이 어떤 WorkItem과 이어지는지 Codex가 빠르게 비교하도록 주는 짧은 상태 묶음이다. 전체 DB를 덤프하지 않고 복구 결과, 다른 세션의 활성 작업과 실행 가능한 후보만 담는다.

  1. check_database_health()로 SQLite를 읽을 수 있는지 확인한다. 실패하면 복구·상태 조회는 중단하고 경고를 전달하며, 이후 PreToolUse가 프로젝트 변경을 막는다.
  2. 현재 session_id의 Binding을 읽고 list_running_runs()로 모든 running Run을 조회한다.
  3. Binding이 정확한 running Run을 가리키고 binding.turn_id != current_turn_id일 때만 recover_stale_run()으로 복구한다. turn_id는 순서 없는 식별자이므로 대소 비교하지 않는다.
  4. Binding의 Run이 running 목록에 없으면 get_run()으로 확인한다. 이미 종료됐거나 존재하지 않으면 finish_work PostToolUse가 놓친 포인터이므로 delete_binding(expected_run_id=...)으로 현재 세션 Binding만 정리한다.
  5. list_running_runs()를 다시 호출해 남은 Run을 active_work_items로 만든다. 다른 세션 소유이거나 Binding이 없는 Run은 자동 변경하지 않는다.
  6. get_project_progress()로 복구가 반영된 진행량을 조회한다.
  7. list_next_work_items(limit=3)로 복구된 항목을 포함한 ready 후보 최대 3개를 priority가 높은 순서, 같으면 오래 기다린 순서로 가져온다.

Hook이 하는 일Hook이 하지 않는 일이유
list_running_runs()로 미종료 Run을 찾고, 현재 세션의 이전 turn 소유가 확인된 항목만 recover_stale_run()으로 복구다른 세션 또는 Binding 없는 Run의 자동 종료다른 세션의 정상 실행을 실수로 중단하면 안 된다.
현재 세션 Binding이 종료됐거나 존재하지 않는 Run을 가리키면 expected_run_id 조건으로 Binding만 삭제다른 세션의 오래된 Binding 추측 삭제finish_work PostToolUse 누락은 복구하되 병렬 세션의 소유권은 침범하지 않는다.
복구 후 running Run을 재조회해 active_work_items를 만들고, 진행량과 ready 후보 최대 3개를 제공사용자 요청의 의미 분류Hook에는 추론 능력이 없고 입력만으로 답이 정해지는 처리만 맡는다.
DB 건강 검사 실패를 경고하고 상태 패킷을 실패 상태로 반환불완전한 DB 상태로 복구·변경 계속단순 답변과 읽기는 계속할 수 있지만 프로젝트 변경은 PreToolUse에서 fail-closed로 막아야 한다.
후보 순서와 필드를 기계적으로 제한WorkItem 선택·생성 또는 Run 시작후보가 이번 요청과 같은 목표인지는 Codex가 판단해야 한다.
DB 장애 시 db_ok: false, 빈 목록과 짧은 경고를 반환부분 조회 결과로 프로젝트 작업 계속일회성 답변은 가능하지만 상태를 기록할 수 없는 프로젝트 변경은 중단해야 한다.
후보가 없다는 사실을 그대로 전달후보가 없다는 이유만으로 새 WorkItem 생성일회성 질문일 수도 있고, 상위 3개 밖에 관련 작업이 있을 수도 있다.

UPS 출력 계약: Hook은 JSON을 <work-selection-context>로 감싸고 “이 패킷으로 $work-start를 실행하라”는 짧은 지시만 함께 보낸다. WorkItem 판단 규칙의 단일 원본은 .agents/skills/work-start/SKILL.md이며 AGENTS.md에는 패킷이나 스킬이 없을 때 변경을 중단하는 최소 안전 규칙만 둔다.

실패는 대체 실행하지 않는다. UPS가 실패하면 db_ok: false, 빈 상태 목록과 짧은 warnings를 반환한다. 패킷이 없거나 DB가 비정상이면 Codex는 일회성 질문에는 답할 수 있지만 프로젝트 작업은 시작하지 않는다. $work-start가 UPS 조회·복구를 대신 호출하지 않는다.

선택 전 제한: 아직 WorkItem이 정해지지 않았으므로 UserPromptSubmit은 get_work_context()나 start_work()를 호출하지 않는다. Acceptance Criteria와 최근 Run처럼 큰 문맥은 후보가 선택된 뒤에만 읽는다.

Codex가 WorkItem을 결정하는 순서

기본값은 새 작업 생성보다 기존 목표 재사용이다. 제목이나 키워드가 비슷한지가 아니라, 이번 요청이 기존 WorkItem의 완료에 필요한지를 비교한다.

1 · 요청 성격 분류

답변으로 끝나는지, 프로젝트를 진전시키는지 먼저 구분한다.

  • 설명만 받고 상태·산출물·다음 행동이 달라지지 않음 → 일회성 답변
  • 설계·조사·의사결정·문서·구현·검증 결과를 이후에도 이어받아야 함 → 프로젝트 작업
  • 코드나 파일을 수정하는지만으로 판정하지 않음

2 · 기존 목표 우선 비교

각 후보의 goal과 next_action을 사용자 요청과 비교한다.

  • “이 WorkItem을 완료하려면 이번 요청도 처리해야 하는가?”가 참이면 재사용
  • 표현·작업 방식·세부 단계가 달라도 같은 완료 목표면 재사용
  • 후보 ID를 사용자가 직접 적었어도 상태와 목표를 확인한 뒤 선택

3 · 검색 한 번 또는 생성

상위 3개에 명확한 후보가 없으면 목록을 더 펼치지 않고 목표 기반 검색을 딱 한 번 실행한다.

  • Codex가 사용자 요청에서 핵심 용어 2~5개를 만듦
  • search_work_items(terms, statuses, limit=5)로 backlog·ready·blocked 검색
  • 유력 결과만 get_work_context()로 상세 확인
  • 그래도 적합한 목표가 없으면 새 WorkItem 생성

검색은 일반 SQL이다. Codex는 사용자 요청에서 “장기 기억”, “recall”, “불러오기” 같은 검색어를 만들고, search_work_items()는 파라미터가 적용된 SQLite LIKE로 title·goal·next_action을 찾는다. 제목 3점, 목표 2점, 다음 행동 1점으로 단순 정렬하며 최대 5개만 반환한다. 반복 검색이나 전체 WI 순회는 하지 않는다.

새 WorkItem을 만드는 충분한 조건

아래 중 하나가 명확해야 한다.

  • 기존 WorkItem과 독립적으로 완료할 수 있음
  • 별도의 목표와 Acceptance Criteria(완료 조건)가 필요함
  • 기존 WorkItem이 끝나도 별도 작업으로 남음
  • 기존 WorkItem에 포함하면 그 목표가 지나치게 넓어짐

단순히 프롬프트 표현이 다르거나, 이번 Run의 수행 방식이 바뀌었거나, 기존 next_action과 정확히 같지 않다는 이유만으로 새로 만들지 않는다.

Feature가 아직 없다면

Feature는 여러 WorkItem을 묶는 큰 작업 영역이다. 프로젝트 초기의 설계·조사에서는 작업 영역이 아직 불분명할 수 있다.

  • feature_id = null인 WorkItem 생성 가능
  • 설계·조사는 research, 선택을 확정하는 작업은 decision 사용 가능
  • 영역이 분명해진 뒤 Feature를 만들고 연결 가능
  • Feature를 먼저 만들기 위해 작업 시작을 미루지 않음

Wrapper는 키워드별 결과를 병합하며, 조회 실패는 이미 생성된 Run을 취소하지 않고 경고만 주입한다. 같은 Hook은 사용자에게 WorkItem·Run·Binding 상태, 프로젝트의 진행 중·준비·완료 개수와 Recall 개수를 짧은 systemMessage로 보여준다. 세션 ID와 Binding 파일 경로는 표시하지 않는다.

프로젝트 작업의 전체 흐름

설계·조사·의사결정·구현·검증에 공통으로 적용한다. 단계를 누르면 실제 책임을 확인할 수 있다.

1. UserPromptSubmitBinding 정리 → 복구 → 상태 패킷
2. 요청 분류·매칭답변 · 재사용 · 검색 1회 · 생성
3. 작업 시작Context → start_work → Recall
4. PreToolUse도구 분류 · 상태 검사
5. 실제 작업설계 · 조사 · 구현 · 검증
6. PostToolUse확실한 Artifact만 기록
7. 검증 연결verify_criterion
8. 기억 FinalizePlan 생성·재사용 · promote · reject
9. 종료 준비finish_work → Binding 삭제
10. Stop Guard통과 또는 1회 계속
1. UserPromptSubmit

DB 건강과 현재 세션 Binding을 확인한다. 다른 turn_id의 running Run은 interrupted로 복구하고, 이미 종료된 Run을 가리키는 Binding은 fallback으로 삭제한다. 그 뒤 running Run을 재조회해 다른 세션의 active WorkItem, 프로젝트 진행량과 ready 후보 최대 3개를 주입한다.

Recall은 키워드별 결과를 합친다

MemoryGraph의 현재 recall --query는 여러 단어를 각각 찾지 않고 전체 문자열을 하나로 검색한다. 따라서 프로젝트 wrapper가 한 입력 문자열을 키워드로 분리하고, 키워드별 결과를 기억 ID로 병합한다.

상위 3~5개만 전달전체 기억과 각 Recall의 원본 출력을 모델 문맥에 넣지 않아 토큰을 제한한다.

구현된 경계: Wrapper는 vendored MemoryGraph의 SQLiteBackend API를 직접 호출하고 안정적인 JSON을 만든다. Hook은 그 JSON에서 Codex에 필요한 제목·요약·매칭 키워드만 추려 additionalContext에 넣는다.

프로젝트 변경 전 활성 Binding 검증

validate_active_binding()은 Runtime Binding을 상태의 정본으로 믿지 않고 현재 Turn과 SQLite의 실제 실행 상태를 한 번에 교차 확인하는 Hook 전용 함수다.

  • 현재 세션의 Binding 파일이 존재해야 한다.
  • binding.turn_id == current_turn_id여야 한다.
  • Binding의 run_id와 work_item_id가 DB에서 서로 연결되어 있어야 한다.
  • Run은 running, WorkItem은 in_progress여야 한다.
  • 검증은 프로젝트 변경으로 분류된 도구에만 실행하며 조회 도구에는 DB를 열지 않는다.

경계 상황확정 정책쉬운 의미
Binding 없음·불일치조회와 create_work_item·start_work만 허용하고, 나머지 변경은 거부한다.현재 요청과 연결된 Run을 모르면 파일이나 상태를 바꾸지 않는다.
DB 열기·조회 실패조회 시도와 작업 준비 호출은 통과시키되, 프로젝트 변경은 거부하고 상태 저장소 점검을 안내한다.DB 상태를 확인할 수 없으면 기존 Run이 있다고 추측하지 않는다.
PreToolUse 자식 정책 실패pre_tool_use_guard.py가 실제 정책 Hook을 최대 7초 동안 실행한다. 비정상 종료, 잘못된 JSON·응답 구조, 내부 시간 초과는 stderr 사유와 Codex 차단 종료 코드 2로 바꾼다. 바깥쪽 Codex Hook 제한 시간은 10초다.정책 검사기가 정상 답을 못 해도 감시 래퍼가 파일 변경 전에 도구를 멈춘다. 래퍼 자체의 강제 종료는 v1 범위에서 제외한다.
경로 검사저장소 루트를 기준으로 실제 경로를 계산한다. 저장소 밖, 외부를 가리키는 심볼릭 링크, .git/, .harness/state.db* 직접 변경을 거부한다.프로젝트 파일만 바꾸며, Git 내부와 DB는 전용 Interface를 통하지 않고 만지지 않는다.
Bash의 불투명한 경로명령에서 확인 가능한 절대 경로와 .. 이탈은 거부한다. 스크립트 내부의 동적 경로처럼 Hook이 볼 수 없는 효과는 Codex 샌드박스·권한 체계에 맡긴다.Hook이 실제로 확인할 수 있는 범위까지만 책임지고 보안 경계인 척하지 않는다.
위험 명령 예외v1은 예외 없이 거부한다. 이후 필요해지면 사용자 승인으로 생성되는 1회성 Permit을 별도 설계한다.초기 구현에서는 위험 명령을 자동으로 풀어 주지 않는다.

  • authorize_tool_call(): 변경 호출이면 validate_active_binding()으로 현재 Turn의 Binding과 DB 상태를 확인해 최종 허용·거부

책임 경계: PreToolUse는 호출 가능 여부만 판단한다. MCP 입력 검증과 WorkItem·Run 상태 전이는 state_store.py가 담당하며, Hook 정책은 Codex 샌드박스·권한 체계를 대신하는 보안 경계가 아니다.

구현된 운영 경계: PreToolUse는 matcher 없는 단일 Hook이 내부 dispatcher로 도구 종류를 나눈다. 외부 MCP는 이 프로젝트의 상태를 바꾼다고 단정할 수 없어 통과시키며, 전역 Hook과 프로젝트 Hook의 충돌 가능성은 하네스가 추측해서 해결하지 않는다. Run 없이 복합 조회 명령이 막힌 경우에는 오류가 아니라 “단순 조회 명령으로 나눠 다시 시도할 예정”이라는 안내를 사용한다.

PostToolUse와 Artifact 기록 정책

PostToolUse는 start_work()·finish_work() 수명주기만 처리한다. 일반 도구 결과는 그 의미를 직접 읽은 Codex가 판단하여 record_artifact() MCP로 저장한다.

대상처리쉬운 의미
start_work()·finish_work()각 도구 전용 PostToolUse가 Binding 저장·Recall 또는 종료 Run의 Binding 삭제를 수행한다.작업 시작과 종료에 꼭 필요한 기계적인 뒤처리만 Hook이 맡는다.
테스트·lint·빌드·커밋Codex가 실제 실행 완료와 결과를 확인한다. 현재 Run의 검증 가능한 산출물이면 record_artifact()를 호출한다.명령과 결과를 모두 본 모델이 저장 가치를 판단한다.
조회·도움말·dry-run·불완전 실행Artifact로 기록하지 않는다. 일반 셸 명령을 자동 분류하는 PostToolUse도 만들지 않는다.실제 작업 결과가 아니면 상태 저장소를 늘리지 않는다.
Criterion Evidence·Run 종료Hook이 처리하지 않는다. Codex가 verify_criterion과 finish_work로 판단한다.결과가 어느 완료 조건을 증명하는지는 모델이 문맥을 보고 결정한다.

일반 결과 기록 순서

  1. Codex가 명령과 실제 결과를 확인한다.
  2. 현재 Run을 검증하는 의미 있는 결과인지 판단한다.
  3. 가치가 있으면 종류·상태·짧은 요약·참조 위치로 record_artifact()를 호출한다.
  4. 특정 Criterion의 근거라면 verify_criterion()으로 Evidence를 별도 연결한다.
ordinary tool result
  → Codex meaning check
  → meaningful: record_artifact()
  → optional: verify_criterion()

not meaningful / incomplete
  → no state write

저장 경계: stdout·stderr 전문, 환경 변수, 비밀정보는 Artifact에 넣지 않는다. DB의 UNIQUE(run_id, kind, uri)가 중복 저장의 최종 방어선이며, OTel Trace 연결과 종료 누락 검사는 후속 단계로 남긴다.

기억 검토·저장work-finishlist_memory_candidates → inspect_memory_candidate → 저장된 Plan이 없으면 Storage Plan 생성, 있으면 Plan 재사용 → finalize_memory_candidate (create·merge 성공 시 내부 promote, reject도 내부 처리)중복·가치·관계 평가는 Skill을 따르는 Codex가 판단한다. 최초 finalize가 State DB에 Plan 원문과 plan_fingerprint를 남기므로, 중단 후에는 새 계획을 만들지 않고 기존 계획으로 빠진 단계만 재시도한다. work-finish는 promote·reject를 직접 호출하지 않는다.
종료 직전Codexget_postflight_status → finish_work전체 완료·정상 진전·재시도·막힘·중단 중 outcome을 Codex가 판단한다.
finish_work 성공 직후전용 PostToolUse도구 응답의 종료 Run ID 확인 → delete_binding(session_id, expected_run_id)종료된 Run의 Binding을 즉시 제거하되, Binding이 다른 Run으로 바뀌었으면 삭제하지 않는다. 실패하면 다음 UPS가 현재 세션에서만 fallback 정리한다.
종료 시도Stopget_running_run(), get_postflight_status()마감 대신 누락만 검사한다.
세션 종료SessionEndTrace flush, 임시 파일 정리늦게 실행돼도 안전한 보조 처리만 둔다.

Hook이 현재 Run과 소유 세션을 찾는 방법

DB에 Codex 세션 필드를 넣지 않고 세션별 Runtime Binding을 별도로 둔다. 서로 다른 WorkItem은 병렬로 실행할 수 있지만, 하나의 WorkItem은 한 세션만 소유한다.

Runtime Binding

Codex의 현재 세션·요청을 WorkItem·Run과 연결하는 임시 포인터다. session_id는 대화 세션, turn_id는 그 안의 이번 사용자 요청을 구분한다. 프로젝트 상태의 정본은 아니며 실제 상태는 항상 SQLite에서 다시 확인한다.

  • .harness/runtime/bindings/<session-id>.json에 세션마다 별도 저장하며 Git에서 제외
  • runtime_binding.py의 save_binding()이 임시 파일과 원자적 교체를 사용하고 파일 권한을 제한
  • load_binding()·find_run_owner()는 손상된 구조와 안전하지 않은 ID를 거부
  • validate_active_binding()은 현재 turn_id가 일치하고 DB의 Run·WorkItem이 각각 running·in_progress인 경우에만 성공
  • delete_binding(expected_run_id=...)은 Binding이 다른 Run으로 바뀌었으면 삭제를 거부
  • start_work가 성공한 경우에만 전용 PostToolUse가 Hook 입력의 세션·turn과 도구 결과의 WorkItem·Run ID로 생성
  • Pre/PostToolUse와 Stop은 현재 Hook 입력의 session_id·turn_id가 Binding과 모두 일치할 때만 사용
  • finish_work 성공을 본 PostToolUse가 해당 세션 Binding을 삭제
  • recover_abandoned_work 성공을 본 PostToolUse는 복구된 run_id를 가리키는 이전 세션 Binding을 찾아 삭제
  • 같은 세션의 다음 turn에서 남아 있으면 UPS가 미종료 Run으로 복구
  • 다른 세션 Binding은 사용자 확인 없는 자동 변경이나 takeover에 사용하지 않으며, 만료 시간과 Lease도 사용하지 않음

Binding 생성 실패 보상: start_work 성공 뒤 Binding 저장이 실패하면 내부 함수 recover_unbound_run(work_item_id, expected_run_id)이 방금 생성된 정확한 Run만 interrupted로 정리하고 WorkItem을 기존 next_action이 유지된 ready로 되돌린다. 이 경우 Recall과 프로젝트 작업은 시작하지 않는다.

병렬 상황처리결과
세션 A와 B가 서로 다른 WorkItem 선택각 세션이 자기 Binding과 Run을 생성병렬 실행 허용
세션 B가 세션 A의 active WorkItem 선택start_work를 호출하지 않고 세션 A에서 이어가도록 안내한다. 세션 A가 종료됐다고 사용자가 확인할 때만 미종료 Run의 중단 처리와 잠금 해제 여부를 묻는다.확인 전에는 새 Run·Binding 없이 기존 상태 유지
사용자가 다른 세션의 종료를 확인Codex가 조회 당시의 expected_run_id와 user_confirmation="confirmed"를 넣어 recover_abandoned_work() 호출정확히 같은 Run이 아직 running일 때만 interrupted·ready로 복구; 이후 start_work()로 새 Run 시작

정본이 아니다. Hook은 Binding의 세션·요청 ID가 현재 Hook 입력과 같은지 확인한 뒤, state_store.py로 실제 WorkItem이 in_progress이고 Run이 running인지 다시 확인한다. 하나라도 다르면 프로젝트 변경을 거부한다. finish_work 성공 직후 전용 PostToolUse가 현재 세션 Binding을 즉시 삭제하고, 누락되면 다음 UPS가 종료된 Run을 확인해 같은 expected_run_id 조건으로 fallback 삭제한다. 두 경로 모두 다른 세션 Binding은 건드리지 않는다.

실패와 예외 처리

Hook이 결과 의미를 추측해 상태를 자동 마감하지 않는 것이 공통 원칙이다.

활성 Run 없이 파일을 수정하려 하면?
설계 문서를 포함한 저장소 변경은 프로젝트 작업이므로 먼저 WorkItem을 선택하거나 만들고 start_work를 호출해야 한다. PreToolUse는 Run 없는 변경 도구를 차단할 수 있다. 단순 질문과 프로젝트 조사 모두 읽기 도구를 쓸 수 있으므로, 읽기 전용 작업의 Run 필요 여부는 Codex가 AGENTS 지침에 따라 분류한다.
start_work는 성공했지만 Binding 저장이 실패하면?
PostToolUse가 recover_unbound_run()으로 방금 생성된 정확한 Run만 interrupted로 정리하고 WorkItem을 ready로 되돌린다. Recall을 실행하지 않고 Codex에 프로젝트 작업 중단을 전달한다. 보상 처리까지 실패하면 유효한 Binding이 없으므로 이후 변경은 PreToolUse가 차단한다.
UPS 패킷이 없거나 db_ok가 false라면?
일회성 질문에는 답할 수 있지만 WorkItem 선택·생성, start_work와 프로젝트 변경은 중단한다. Codex나 $work-start가 UPS의 DB 건강 검사와 stale Run 복구를 대신 실행하지 않는다.
Binding이 없거나 DB 상태를 확인하지 못하면?
조회 도구와 WorkItem·Run 준비 도구는 허용한다. 파일·DB 상태를 바꾸는 호출은 거부하며, 기존 running Run을 추측해서 자동 연결하지 않는다. UPS 복구도 현재 세션의 이전 turn Binding으로 소유를 확인할 수 있을 때만 실행하고, 확인할 수 없으면 recovery_warnings로 Codex에 알린다.
finish_work는 성공했지만 Binding 삭제 Hook이 실패하면?
성공한 Run·WorkItem의 DB 상태는 되돌리지 않는다. 다음 Turn의 UPS가 현재 세션 Binding의 run_id를 조회해 Run이 이미 종료됐거나 존재하지 않으면 delete_binding(expected_run_id=...)으로 Binding만 정리한다. 다른 세션 Binding은 fallback으로 삭제하지 않는다.
다른 turn ID의 running Run을 발견하면?
list_running_runs()로 찾은 뒤 Runtime Binding이 현재 세션에 속하고, binding.turn_id != current_turn_id이며, 해당 Run을 가리키는지 확인한다. 세 조건이 모두 맞으면 recover_stale_run()이 Run을 interrupted로 종료하면서 종료 시각, “다른 turn에서 finish_work 없이 종료됨”이라는 기계적 요약과 종료 이유를 남긴다. turn_id는 순서 없는 식별자이므로 대소 비교하지 않는다. WorkItem은 기존 next_action을 유지한 채 ready로 돌리고 오래된 Binding을 삭제한다. Codex는 현재 요청과 복구된 WorkItem의 목표를 비교해 같은 WorkItem에 새 Run을 만들지 판단한다.
다른 세션이 같은 WorkItem을 작업 중이면?
현재 세션은 새 Run과 Binding을 만들지 않고 원래 세션에서 이어가도록 안내한다. 사용자가 원래 세션이 종료됐다고 알려주면 Codex가 “남은 Run을 interrupted로 종료하고 WI 잠금을 해제할까요?”라고 확인한다. 이 동작은 기존 Run의 정상 성공 종료나 재개가 아니며, 명시적인 동의 전에는 상태를 변경하지 않는다.
다른 세션이 사라져 WorkItem이 계속 잠겨 있으면?
사용자는 CLI 명령이나 세션 ID를 알 필요가 없다. Codex가 충돌 정보의 WorkItem ID와 Run ID를 보관해 두었다가 명시적 동의 후 recover_abandoned_work()를 호출한다. 함수는 expected_run_id가 여전히 해당 WorkItem의 running Run일 때만 기존 Run을 interrupted, WorkItem을 기존 next_action이 유지된 ready로 원자적으로 복구한다. 그 뒤 Codex가 start_work()를 별도로 호출해 현재 세션의 새 Run을 만든다. Lease·시간 만료·자동 takeover는 사용하지 않는다.
위험 명령이 정말 필요하면?
v1에서는 활성 Run이나 사용자 요청만으로 예외를 만들지 않는다. 실제 필요 사례가 생기면 사용자 승인을 한 번만 소비하는 Permit 구조를 별도로 설계한다.
어떤 기존 WorkItem을 선택하나?
기본값은 재사용이다. “기존 WorkItem을 완료하려면 이번 요청도 처리해야 하는가?”가 참이면 같은 WorkItem에 새 Run을 만든다. 독립적으로 완료할 별도 목표와 완료 조건이 필요할 때만 새 WorkItem을 만든다.
후보 세 개와 맞는 WorkItem이 없다면?
Codex가 사용자 요청에서 핵심 용어 2~5개를 만들고 search_work_items()를 딱 한 번 호출한다. 함수는 backlog·ready·blocked WorkItem의 제목·목표·다음 행동을 일반 SQL로 검색해 최대 5개를 반환한다. 그 결과에도 적합한 목표가 없으면 새 WorkItem을 만든다.
테스트는 통과했지만 Criterion과 연결되지 않았다면?
Codex가 먼저 record_artifact()로 결과를 저장하고, 해당 결과가 Criterion의 근거라면 verify_criterion()으로 Evidence를 연결한다. 향후 Stop Guard는 이 연결 누락을 알리고 한 번 계속한다.
작업이 실패하거나 막혔다면?
Codex가 finish_work에서 retry_needed, blocked 또는 interrupted를 선택하고 다음 Run이 이어갈 next_action과 종료 이유를 기록한다.
이번 Run은 성공했지만 WorkItem은 아직 남았다면?
finish_work(outcome="progressed")로 종료한다. Run은 succeeded, WorkItem은 ready와 새 next_action으로 남아 다음 Run에서 이어진다.
pending 기억 후보가 남았다면?
work-finish가 후보를 inspect한 뒤 저장 Plan이 없으면 만들고, 있으면 그대로 재사용해 finalize_memory_candidate()를 호출한다. 부분 실패 후보는 pending으로 남으며 다음 마감 시 저장된 Plan으로 빠진 쓰기만 재시도한다. 같은 이유의 반복은 한 번으로 제한한다.
한 번 더 실행해도 정리하지 못했다면?
무한 반복하지 않는다. 같은 이유의 재시도는 한 번으로 제한하고 Run을 보존한 채 남은 누락과 사용자 조치 필요성을 보고한다.
